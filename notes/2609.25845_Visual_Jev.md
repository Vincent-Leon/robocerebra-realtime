## 一句话总结

把"对同一张图像提出多个相互独立的强制选择题"建模为共享上下文工作负载：图像 + 公共文本前缀只编码并 prefill 一次，N 个问题后缀在 fork 出的前缀 KV 上作为一个 batch 并行前向，直接在 `Answer:` 位置从骨干 LM head 读取候选选项 token 的 logits 并在合法候选内 softmax（Eq. 1）；质量靠 answer-supervised LoRA（四基准 macro 0.706→0.761，增益集中在训练过的两个任务族），效率靠"前缀复用 × 批处理"（N=32 时 warm 摊销时间 50.7→5.7 ms/问，8.9×；但 32 问的组完成时间约 182 ms，峰值显存 8.40→10.10 GiB）。

## 问题设定与动机

- 应用场景是让 VLM "decide rather than to write"：which button cancels an order / whether a banner reports success / how many seats are free（p.1）。候选集在请求时已知，且多个独立问题常共享同一张图像。
- 逐问题执行的两个浪费：为固定选择题解码自由文本；为每个问题重算图像（p.1）。
- 核心系统问题：高效回答关于一张图像的多个独立问题，避免重复视觉计算且不牺牲决策质量；为此必须分离三个因素的效果——任务适配（训练）、输出读出（LM head vs typed head）、服务优化（复用与批处理）（p.1）。
- 形式化（p.2–3）：一个实例 = 图像 I、公共文本上下文 S、问题集合 Q。每个问题独立回答：可读 I、S 与自身文本，不可读其他问题及其答案。作者强调正是这种隔离"licenses the shared execution"（p.3）。
- 定位：post-training 是**质量干预**，shared batched execution 是**服务干预**；typed decision head 与 evidence-sufficiency head 只是对照，不属于推荐系统（p.1，Fig. 1 p.2）。

## 核心设计

### "Jev" 指什么

- **论文正文（含附录）未解释 "Jev" 一词的来源或缩写**——未在论文中找到。
- 从论文用法看，"Visual Jev" 指一种决策接口：运行时提供候选集、每问独立、概率输出、显式问题隔离（贡献 1，p.1）。
- [代码仓库] README 写 "The project extends the Jev-style decision interface to vision"，请求格式是带命名 `questions` 与共享 `state` 的 JSON；还提到 "we did not measure the latency of another Jev service"，并有脚本 `code/vdm/eval/external_openjev.py` 评测一个外部 "OpenJev" 视觉 NLI checkpoint（不同骨干、固定三分类头，只能占 SNLI-VE 一格）。可见 "Jev" 是先于本文存在的决策接口/服务名称，本文是其视觉版本；原始出处未在论文中找到。
- 对我们而言，计划文档中的"Jev 式候选概率"就是 Eq. (1) 的读出方式：候选选项字母的单 token logit 在 K 个合法候选内归一化。

### 共享视觉上下文如何编码与复用 KV

- **Prompt 结构**（p.3）：shared prefix = system turn + image + public context S。每个 suffix = 一个问题 + 其候选 + 固定的 `Answer:` 读出位置。Choice 类型接受运行时给定的 K ≤ 16 个候选；Claim 类型固定三候选 supported / contradicted / not determined；超过上限直接拒绝而非截断。
- **执行流程**（p.3）：(1) 验证前缀 tokenization 对每个问题完全相同；(2) 前缀 prefill 一次；(3) 其 KV 状态沿问题分支扩展；(4) 填充后的后缀作为单个 batch 运行；独立 batch 行隔离各后缀，attention mask 屏蔽 padding。
- **为什么前缀 KV 足够**（p.2、p.3）：Qwen3-VL 以 DeepStack 方式只在前三个文本层的图像 token 位置重新注入视觉特征，这些位置全部位于缓存前缀内，因此后缀前向不需要任何额外视觉特征。图像 token 使用多轴 RoPE（M-RoPE），作者指出这两个细节"matter for what can be shared across questions"。
- **两级复用**（Table 3，p.5）："vision cache" 只复用视觉编码器输出、仍重跑整段语言序列；"prefix share" 复用整个前缀的 KV。
- [代码仓库] 实现细节（`vdm_model.py`）：`_prefill_prefix` 用 HF `DynamicCache` + `use_cache=True` 跑 `language_model`；`_fork(cache, batch)` 对每层 K/V 先 `expand(batch, ...)` 再 `.contiguous().clone()`——即**物理复制 N 份前缀 KV**，注释写明 "The copy is a real cost of the shared path and the benchmark reports it separately rather than folding it into the prefill"；后缀前向传 `deepstack_visual_embeds=None`；3-D M-RoPE 位置 id 用 `get_rope_index` 对全序列计算一次再切片，保证共享与独立路径位置完全一致。
- 小出入：论文 p.3 写 "right-padded suffixes"，而代码 `run_prefix_share_batch` 的注释写后缀 **left-padded**，使读出位置对齐到每行最后一列。以代码为准更合理；引用时不要复述填充方向。

### 候选问题如何批处理

- 一组 N 个问题取自同一张 GQA 图像（p.4）；N ∈ {1, 2, 4, 8, 16, 32}（Table 13，p.13）。
- 复用（reuse）与批处理（batch）是两个正交因子，做了 2×3 交叉实验（Table 3，p.5）："batching" 指 N 个后缀作为一个 padded batch 一次前向；"sharing" 指复用视觉输出或前缀 KV。
- 批内隔离：每个问题独占一行、无跨行注意力（Fig. 1 "branches never see each other"，p.2）。
- 批处理的前提是问题**同时已知**（co-available）；论文不处理独立到达的请求，也不含排队（p.7）。

### 候选概率 / 打分如何得到决策

- Eq. (1)（p.3）：p(c_j | I, S, q) = exp z_j / Σ_{ℓ=1..K} exp z_ℓ，其中 z_j 是候选 j 对应选项字母的"verified single token"在 LM head 上的 logit。归一化只覆盖该问题给出的 K 个候选；训练仍是全词表 next-token CE。
- 决策 = 候选内 argmax；**不生成任何 token**，只读一次 `Answer:` 位置的 logits。
- 对照读出（p.3）：同一位置的 layer-normalized hidden state 送入 16-slot Choice head 或 3-way Claim head，用合法 slot 上的 CE 训练；另有标量 evidence-sufficiency head 仅在附录评估。所有头与默认系统共享骨干、数据、prompt、步数预算。
- 作者在 Ethics 节明确：该候选概率**不是**校准后的"答案正确"概率；附录 A 显示模型可在证据被移除的观测上依然自信（p.7）。

### 是否需要训练、训练数据与目标

- **机制本身不需要训练**：未训练的 4B backbone 直接通过 LM head 读出即得 macro 0.706（Table 2，p.5）；训练只是为了提升质量。
- **默认系统 = answer-supervised LoRA（"answer SFT"）**：目标是普通 next-token CE，不加任何头（p.3；附录 C p.13 "Answer SFT trains no additional head"）。
- **数据**（p.3）：30,416 条 GQA Choice 样本 + 9,000 条 SNLI-VE Claim 样本；3,000 updates × batch size 8（= 24,000 个样本，不足一个 epoch——我的换算）；Choice 样本 K 在 2–8 间变化并打乱选项顺序；主系统 3 个 seed。TextVQA 与 TallyQA 完全 held out。
- **超参与硬件**（附录 C p.13）：Qwen3-VL-4B-Instruct，bfloat16，视觉塔冻结，LoRA r=16、α=32、dropout 0.05 作用于语言塔 attention 与 MLP 投影；AdamW + 余弦调度、100 步 warm-up、LR 1e-4（LoRA）/ 1e-3（heads）、梯度裁剪 1.0、batch 8 + 梯度检查点、视觉 token 预算 196（448×448）；单卡 RTX 5090（32 GB）约 45 分钟/变体，峰值显存 14.4 GiB；诊断头用 float32，最大配置 33.1M 可训练参数。8B 对照只换骨干规模。

### 推理服务层实现细节

- **不基于 vLLM / SGLang**：论文仅在相关工作中引用 Orca、PagedAttention(vLLM)、SGLang、FlashAttention、MQA/GQA 作为"标准杠杆"（p.2）；自身软件栈为 PyTorch 2.14 + CUDA 13.0 + Transformers 5.17（p.13）。[代码仓库] `requirements.txt` 仅 `transformers==5.17.0`、`peft==0.21.0`、`accelerate` 等，无 vLLM/SGLang；执行路径是基于 HF `Qwen3VLForConditionalGeneration` 的自定义代码。
- **prefix caching 的实际用法**：单图、单组内的一次性 prefill → fork（物理复制）→ 批后缀前向；**没有**跨请求/跨组的 radix 或 paged 前缀缓存，**没有**连续批处理，**没有**请求排队。论文中 "KV cache" 就是指这个组内复用。
- **计时口径**（p.3–4）：同步 `time.perf_counter`，warm 测量（丢弃 2 次预热后取 5 次），起点是内存中已解码图像与已提取问题记录；**包含** processor/tokenization、host-to-device 传输、模型执行；**不含**图像解码、记录构造、磁盘/网络 I/O、服务队列。N>1 时"每问时间 = 组完成时间 / N"，作者反复强调这是摊销吞吐、不是单请求延迟（Fig. 2 caption p.4；p.4；p.7）。

## 实验与主要结果

### 任务与基准（p.3；Table 1）

- GQA（object/attribute/relation，天然多问同图的主要来源）、SNLI-VE（Claim）、TextVQA（文字阅读，held out）、TallyQA（计数，held out）。开放答案转换为 Choice 候选集，不与开放式榜单比较；split 按父图像隔离。
- 盲基线诊断（Table 1，p.3；Chance / Grey-image / Sighted，均为原始骨干在诊断子集上的结果）：TextVQA(K=8) 0.125 / 0.369 / 0.974；GQA(converted) 0.365 / 0.585 / 0.841；SNLI-VE(Claim) 0.333 / 0.334 / 0.637；TallyQA 0.167 / 0.209 / 0.357。
- 第一版 TextVQA 转换因使用全局答案池做干扰项、盲准确率超过 99% 而被重建为同模板干扰项（p.3）。

## 与本项目的关系

对照计划文档第 6 节（同模型共享上下文的快慢并行推理）与第 8.2 节（关键消融）。

### 可直接用于快分支的机制

1. **LM-head 候选读出（Eq. 1）** 即 6.1 中快分支的"Jev 式候选概率"：零训练即可用（0.706 的原始骨干结果证明机制与训练无关），一次后缀前向、不解码；K ≤ 16 个候选用单 token 选项字母表示；运行时候选集可变。可直接作为 8.2 "候选打分 / 短文本输出 / 独立问题批处理"消融中的"候选打分"实现。
2. **一次 prefill + fork + 各自后缀**：对应 6.1 "共享前缀做一次 prefill"与 6.2 "两分支共享只读前缀，分叉后各自维护后缀 KV；不共享可变解码状态"。论文的 `_fork` 就是这一边界的最简实现。
3. **复用条件的具体化**：论文要求前缀 tokenization 逐 token 相同（p.3），并给出 Qwen3-VL 的两个条件——DeepStack 注入位置全部在前缀内、M-RoPE 3-D 位置 id 需按全序列计算再切片——正是 6.2 第 1 条"token、视觉表示、位置和注意力设置完全兼容"在具体模型上的落地。若我们用 Qwen3-VL 系列，可直接沿用。
4. **匹配条件的实验设计**：crossed reuse × batching、同输入同硬件同并发、warm 预热、同时报告准确率/不一致数/峰值显存，直接对应 8.2 "共享／不共享 KV 时匹配输入、硬件、并发和缓存预热条件"。Table 3 + Table 11 的格式可作为我们效率表的模板。
5. **盲基线检查**：灰图诊断（Table 1）提醒我们：动作选择题也要报告"只看任务规则与历史、不看观测"能猜中多少，否则候选集可能泄露答案。

### 他们没做、我们必须扩展的部分

- **只有静态单图、问题同时已知**（p.7 "The workload requires co-available questions"）。没有任何跨帧更新实验。按 6.2 第 4 条，新观测到来时前缀中的图像变化，整个前缀必须重新 prefill 或改为追加观测的历史流；论文对这类成本毫无数据。
- **N=1 负收益的含义**：若每帧只问 1 个问题且每帧重建前缀，Jev 式共享本身是亏的（82.9 vs 48.1 ms）。在我们的设计里共享要回本，必须让同一前缀上跑多个后缀——快分支的问题 + 慢分支的规划问题——这正是 RQ3 要验证的"观测和计划更新成本计入后，共享前缀仍能降低重复 prefill 开销"。
- **只有判别式后缀，没有生成式后缀**。慢分支是长解码；论文 "generate, joint" 133 ms 和 "skipping token generation is not the main saving" 说明一旦涉及串行解码，节省的 prefill 不再是瓶颈，而快慢并发会争抢算力与带宽（6.4）。论文没有并发两类负载的实验。
- **没有分支协调**：无计划版本、无取消、无观测刷新、无调度器；排队延迟被明确排除（p.7）。6.3、6.4 的全部内容都在论文之外。
- **前缀完全只读**；我们的"有效计划"在前缀里会随慢分支发布而改变，触发 6.2 第 5 条的缓存失效与重建开销，论文未涉及。
- **概率不校准**（p.7）。若用候选概率的熵/margin 触发慢分支（FASIONAD 式不确定性触发），需要自建校准或风险估计；附录 A 还表明额外的 sufficiency head 也不能改善 selective prediction。

### 为什么计划文档要求"Jev 式批处理必须报告每帧问题数"

- 论文的全部效率收益是 N 的函数（Table 13）：N=1 共享为负收益，N=4 持平，N=32 才达到 8.9×。5.7 ms 是 182 ms / 32 的摊销值，作者自己在三处强调它"not single-request response latency"（Fig. 2 caption p.4；p.4；p.7）。
- 机器人快分支每帧通常只有 1 到少数几个决策问题，受约束的是**单帧决策延迟（组完成时间）**，不是吞吐。若不报告每帧问题数，把 N=32 的摊销数字当作"动作延迟"就是误用——这正是计划文档 8.2 末尾那句话的依据。
- 显存随 N 增长（8.40→10.10 GiB；[代码仓库] 因为 fork 是物理复制），同硬件下会挤占慢分支的 KV 空间，因此每帧问题数也影响 RQ6 的同硬件对照。

## 局限与注意点

论文自述（Limitations，p.7）：
- 收益依赖问题同时可用；独立到达的请求组批会引入其基准排除的排队延迟。
- 单一骨干家族（Qwen3-VL 4B/8B）、英文、K ≤ 16、视觉塔冻结（可能限制细粒度任务）。
- 无跨任务迁移证据；置信区间只覆盖测试采样不覆盖训练随机性；固定步数预算，调度与损失权重未充分搜索。
- Choice 转换带语言先验：灰图下 GQA 仍 58.5%（随机 36.5%）。
- 附录证据区域来自 GQA 场景图而非人工标注；evidence sufficiency ≠ correctness。

我的补充：
- 全部计时是单 GPU、无并发其他负载的 warm 微基准；与我们端到端实时评测（含仿真、协调器、排队）口径不可比。
- 由于 fork 物理复制前缀 KV，显存与 N 线性相关；论文未报告 prefill、fork、后缀前向各自的时间分解（代码注释称 benchmark "reports it separately"，但正文表格中未见——未在论文中找到）。
- 右/左填充描述在论文与代码之间不一致（见上）。
- 8B 上 SFT 使 held-out 的 TallyQA 下降（0.429→0.402），说明 answer SFT 对未训练任务可能轻微负迁移。
- 不一致预测（最多 20/7,532）虽小，但在我们的决策闭环中单个翻转可能改变动作；若需逐样本一致性应考虑 float32 读出或接受差异并报告。
- 评估数据均为 VQA 类静态数据集，没有机器人/具身任务；论文无任何动作选择或时间约束实验。
