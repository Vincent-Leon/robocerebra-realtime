## 一句话总结

论文把"模型思考期间环境仍在演化"形式化为 real-time reasoning 问题，构建了以 token 计时、可独立调节认知负荷（cognitive load）与时间压力（time pressure）的 Real-Time Reasoning Gym（Freeway / Snake / Overcooked 三款游戏），实证表明只做快速反应（reactive）或只做长程规划（planning）的单范式 agent 分别在高认知负荷或高时间压力下崩溃，并提出 AgileThinker：规划线程在冻结的观测快照上持续推理，反应线程在每个环境步的末尾结合最新观测与规划线程的（部分）推理轨迹输出动作；在负荷和压力升高时稳定优于单范式基线，且该优势在 wall-clock 实验中得以保持。

## 问题设定与动机

- **核心观察（p2）：** 现有 LLM agent 工作几乎都假设"环境只在 agent 发出动作时才变化"，忽略了世界与 agent 的计算并行演化这一事实。因此"如何评测并提升及时决策能力"是一个开放问题。
- **real-time reasoning 的定义（p3）：** 与 OpenAI Gym 式回合制循环（`agent.think()` 阻塞直到完成）不同，Real-Time Reasoning Gym 的环境以固定速率推进，`agent.think(timeout=T_E)` 超时后若没有动作则用 `DEFAULT_ACTION`（Figure 2，p3）。环境既不因 agent 计算而延迟，也不加速。
- **三个 desiderata（p3）：** (1) dynamic：状态持续更新，不等待 agent；(2) cognitively challenging：任务需要逻辑推理；(3) reproducible：用仿真避免硬件噪声。第 (3) 点直接导出了"用 token 数做时间代理"的设计。
- **两种部署范式（p2, p5）：** reactive agent 用有界推理计算换取响应速度；planning agent 允许跨多个环境步的扩展推理。论文论点是两者都不够：planning 无法应对环境变化，reactive 缺乏战略性（p2）。
- **三个研究问题（p2）：** RQ1 环境因素（负荷、压力）如何影响 agent 表现；RQ2 AgileThinker 中反应与规划资源如何平衡；RQ3 token 仿真结果与真实 wall-clock 实验是否一致。
- **与双系统理论的关系：** 引言以 dual-process theory（Kahneman 2011; Evans & Stanovich 2013）为动机（p2），但 Limitations 明确声明没有任何实证证据表明 AgileThinker 精确建模了人类双系统（p11）。

## 核心设计

### 基准：Real-Time Reasoning Gym

**环境与任务（Table 1 p3；§2 p3–4；App. A p15）**

| 游戏 | 动态要素 | 认知负荷因子 | 评测指标 | 关键规则（p15） |
| --- | --- | --- | --- | --- |
| Freeway（仿 Atari 同名游戏） | Hazards：双向车流持续移动 | 过马路的最少步数 S | 到达对岸所用步数（被撞则重置到起点） | 每步上/下一车道或停留；步数上限 M = 100；R(τ) = M − \|τ\| |
| Snake | Opportunities：食物出现后限时消失 | 障碍物数量 N | 碰撞前吃到的苹果数 | 四方向移动，撞墙/障碍/自身即死；食物持续刷新并在固定步数后消失；M = 100；R(τ) = 吃到的食物数 − 𝟙[在 M 步内死亡] |
| Overcooked（基于 HumanCompatibleAI/overcooked_ai） | Partners：脚本化搭档按非平稳策略自主行动 | 内部厨房柜台长度 L | 双方合作完成的订单数 | 完全可观测双人合作游戏；搭档随机选择"把洋葱送到任意锅或柜台"的策略；M = 100；事件奖励：从分配器取盘 3、从锅取汤 5、上菜 20（Table 3） |

- **难度等级（Table 5 p16）：** Freeway S ≤ 12 / 13 ≤ S ≤ 16 / 17 ≤ S ≤ 21；Snake N = 1 / 2 ≤ N ≤ 5 / 6 ≤ N ≤ 8；Overcooked L = 0 / 3 / 4，分别对应 easy / medium / hard。
- **分数归一化（p5, p15）：** S = (R − R_min)/(R_max − R_min)，R_min/R_max 取全部轨迹中的经验极值：Freeway 0/89，Snake −1/15，Overcooked 0/56（Table 4 p15）。

**时间模型：token 时间为主，真实时间为验证**

- **token 时间（p4）：** 理由是 LLM 解码时间随输出长度近似线性（T = N_T × TPOT），而长序列下 prefill 时间"可忽略"。环境每当 agent 生成 N_{T_E}（图中记为 `T_E`）个 token 就推进一步。四档时间压力：32k / 16k / 8k / 4k tokens/step，由低压到高压（p5）。
- **默认动作（p5）：** Freeway 与 Snake 为"沿上一步方向继续"，Overcooked 为"原地不动"。
- **真实时间（§6 p10；App. D p30）：** 用 DeepSeek 官方 API 拟合 T = αN + β，得 α = 0.0473 s/token，β = 334.55 s，R² = 0.9986（Figure 10 标注 R² = 0.999）。据此把 T_E = 6 分钟视为约 8,000 tokens/step 做 wall-clock 实验（Table 2）。附录另有 DeepSeek-V3.2 在 350 秒/步、Hard 难度下的 wall-time 实验（Table 9 p26）。
- **（仓库）两种时间单位的实现：** `--time_unit token` 时 `agent.think(timeout=8192)` 以解码 token 数计；`--time_unit seconds` 时 `agent.think(timeout=5.0)` 以 wall-clock 计。两种模式下环境都是在 `think` 返回后才 `env.step` 一次，即"真实时间"是 agent 侧的固定决策窗口，而不是自由运行的仿真器。
- **（仓库）token 模式下并行线程是模拟的：** 据 `agents/base.py` 的代码摘要，planning 推理在 token 模式下一次性生成完整输出，再按每步 `budget` 个 token 的切片逐步"释放"给反应线程（`gen_accum`、`gen_text` 等字段）；只有 seconds 模式才用后台守护线程真正流式生成。这意味着论文主实验的 token 时间结果假设两线程完全并行且互不干扰。

**难度维度（p4）**：两条正交轴——cognitive load（任务本身的推理深度）与 time pressure（每步可用 token）。论文期望分数随两者上升而下降，而"具备实时推理能力的 agent 下降得更慢"（p5）。

**观测与动作接口**

- 观测为纯文本状态描述，无图像。Freeway 示例（p17–19）：当前回合、玩家位置、每条车道上各车的 (head, tail, direction, speed)。Snake 为网格与食物（含剩余寿命），Overcooked 为完整状态。（仓库）观测 dict 含 `state_string`、`game_turn`、`state`。
- 动作：Freeway U/D/S；Snake 四方向（仓库 README 另含 S）；Overcooked 四方向 + I（interact）+ S（仓库）。单步动作以 `\boxed{a}` 输出（p8, p18）；多步计划以动作序列输出，如 `\boxed{LLUUUUU}`（p8）或"Turn t1: a_{t1} …"（p16）；code-as-policy 输出 Python 函数 `next_action(json_state) -> str` 外加一句话策略摘要（p21–22）。
- 动作瞬时生效、离散、无耗时、不可"中断"；环境每步只接受一个动作。

**评测协议（§4 p6–7；App. C p23–25）**

- 两组实验：(1) 固定时间压力 8k tokens/step，变化认知负荷 E/M/H，reactive agent 的内部预算 N_i = 8k；(2) 固定 Medium 负荷，变化时间压力 {4k, 8k, 16k, 32k}，N_i = 4k 以保证低于最小预算（p6–7）。
- 每个设置跑 32 次 = 8 个游戏种子 × 4 个 LLM 采样种子，报告平均分（p7）。
- 显著性检验：按环境配置种子配对的单侧 paired t-test，自由度 n − 1，α = 0.05（p24–25）。
- 模型固定为同一家族以保证公平：DeepSeek-V3（reactive）与 DeepSeek-R1（planning），并明确指出 gym 用于比较"固定模型族下的 agent 设计选择"，跨模型比较因 tokenizer 与架构差异可能不公平（p5）。附录补充 DeepSeek-V3.2（thinking off 作 reactive、thinking on 作 planning）与 Gemini-2.5-Flash（p25–27）。

### 方法：两类单范式 agent 与 AgileThinker

**Reactive agents（p5）：** 以 token 预算 N_i ≤ N_{T_E} 约束，每个环境步产生一个新动作。两种实现：非思考模型（V3）直接短输出；思考模型（R1）用 budget forcing（Muennighoff et al., 2025）在预算处截断。

**Planning agents（p5）：** 跨多个环境步推理。两种计划格式：(1) 多步动作序列；(2) code plan，由思考模型生成按观测自动产生动作的代码（code-as-policy，Liang et al., 2022）。后者更能适应变化，但更难生成。

**AgileThinker 架构（§3 p6；Figure 4 p6）**

- 两个并行线程：**planning thread P** 运行一个 LLM（主实验为 R1），对冻结的游戏状态流式生成一个多步计划的思考过程；"一旦初始化，推理过程持续到计划执行完毕"。P 跟不上环境变化（Figure 4 步骤 1–2），但因其关注长期目标，很多推理片段在较长时间内仍有用。**reactive thread R** 运行另一个 LLM（主实验为 V3），在严格时限 T_R ≤ T_E 内，基于最新观测与 P 的（部分）输出做决策。
- **并行与时分协议（p6）：** 每个环境步内 P 持续运行，R 只在最后 T_R 个时间单位内激活。超参数 T_R 控制两线程的资源权衡：T_R 越大 R 越能适应变化，但可参考的 P 推理越少。
- **交接方式（p6, p18；仓库）：** P 的推理轨迹（含 `<think>` 内未完成的部分）以文本形式作为"Guidance from a Previous Thinking Model: Turn t1 = …"段落插入 R 的 prompt（仓库代码按行加 `> ` 引用后拼入）。R 每步输出一个 `\boxed{a}` 动作。（仓库）P 的计划从不被直接执行，所有动作都来自 R；P 完成一个计划后才会在新观测上开启下一轮推理。主实验中 P 与 R 是两个不同模型（V3 + R1），V3.2 实验中则是同一模型的 thinking/non-thinking 两种模式（p25）。
- **处理过时推理（p18, p7）：** 没有程序化的计划有效性检查。R 的 prompt 明确告知：该指导"在回合 t1 基于当时观测计算，可能已不再完全匹配当前情况"，应作为"strategic reference, not a mandatory instruction"，并要求 R 自行判断"原策略在当前动态下还有多少仍然有效"。论文把这视为 AgileThinker 相对纯 planning agent 的关键差异："reactive thread in AgileThinker is informed of the latest state, thus able to adjust the output of planning thread"（p7）。过时程度、被采纳/被拒绝的比例均未量化。
- **与既有双系统方法的区别（p2, p11）：** 先前方法（Christakopoulou et al., 2024; Liu et al., 2024; Zhang et al., 2025）要么两系统独立运行，要么一方必须等另一方完成才能读取输出；AgileThinker 的 System 1 可以读取 System 2 的部分推理轨迹。
- **（仓库）兜底机制：** 若 R 输出中无 `\boxed{}`，追加 `\boxed{` 强制再生成 1 个 token，最多重试 3 次，否则回退到 `DEFAULT_ACTION`。

## 实验与主要结果

**基线（p3, p7, Table 6/7）：** Reactive (V3)、Reactive (R1 + Budget Forcing)、Planning (R1，多步动作序列)、Planning (R1 + Code-Policy)、AgileThinker (V3 反应 + R1 规划)。

### token 时间抽象下的结果

**主结论（跨三款游戏平均，Figure 1 p1；§4 p7）**

- Reactive (V3) 在认知负荷升高时从 0.89 跌到 0.15，AgileThinker 从 0.88 到 0.50（p7）。失败模式：贪心追逐眼前收益、陷入可预见的陷阱（Figure 6 p8 的 Snake 案例）。
- Planning (R1) 在时间压力升高时从 0.92 跌到 0.05，AgileThinker 从 0.90 到 0.58（p7）。失败模式："obliviousness to environmental changes, executing plans based on outdated observations"——Snake 案例中按过时计划撞墙（p7–8）。
- 相对最优单范式方法的优势（Figure 1 下图标注，按分数差 ×100 计）：Medium +35.0、Hard +17.9；8k +35.4、4k +19.8。笔者据 Table 6/7 复算一致；同时在 Easy 与 32k 两个最宽松设置下 AgileThinker 略低于最优单范式方法（约 −0.006 与 −0.026），论文正文未强调此点。
- 两种变体都不够：R1 + budget forcing 无法在不损害质量的前提下缩短生成，平均分甚至低于 V3 reactive（0.01 < 0.39，时间压力系列）；截断通常导致 no-op（p9）。code-policy 在有简单算法解的 Freeway 有效，但在需要启发式搜索或 Theory-of-Mind 的 Snake / Overcooked 不如直接生成动作（p9；代码样例见 App. C.4 p27–29）。

**显著性（Figure 8 p25）：** 相对 reactive 的优势在 Medium/Hard 且压力 ≥ 8k 时普遍显著（p = 0.00），在 Easy 或 4k 下多数不显著（如 Freeway 4k Hard p = 0.20，Snake 4k 全部不显著）；相对 planning 的优势在 8k 与 4k 下几乎全部显著，在 32k 下均不显著（Snake 32k 甚至 Planning 0.9629 > AgileThinker 0.8281）。论文的表述是优势"随负荷与压力增加而普遍变得显著"。

**资源分配（§5 p9；Figure 7）：** 固定 N_{T_E} = 8k，扫描反应线程预算 N_{T_R}。太小（0.5k）则 R 来不及消化 P 的指导；太大则 R 完成后空闲而 P 的有效推理被挤占。性能峰值出现在 N_{T_R} 接近 R 不截断时自然 token 用量的上界（由 CDF 读出）：Freeway 约 5k，Snake 与 Overcooked 约 2k。论文称在较宽的预算区间内 AgileThinker 都优于单范式基线，粗略估计上界即可。

**同等吞吐对照（App. C.5 Table 11 p29–30；数值与 Table 6 的 Medium/8k 一致）：** 把 AgileThinker 改为两线程交替推理（concurrent generation，总 token 吞吐与单模型相同）：Freeway 0.72 / Snake 0.58 / Overcooked 0.85，仍远高于 Reactive (V3) 0.32 / 0.49 / 0.37 与 Planning (R1) 0.22 / 0.03 / 0.09；完全并行为 0.84 / 0.54 / 0.92。论文由此推断收益"主要来自认知分工而非计算资源"（p30）。注意这里的"同等吞吐"是按 token 交替模拟，不是真实硬件上的资源竞争测量。

**其他模型（App. C.3 p25–27）：**
- DeepSeek-V3.2 同一模型两种模式（Table 8 p26，Hard）：AgileThinker 在 32k/16k/8k 均最高（Freeway 0.8889 / 0.8328 / 0.6352），但在 4k 极端压力下 Freeway（0.4466 vs 0.4659）与 Overcooked（0.4486 vs 0.5246）低于纯 reactive (thinking off)，Snake 略高（0.2738 vs 0.2556）。
- Gemini-2.5-Flash（Table 10 p27，Medium Freeway）：因无法访问推理轨迹，采用"reactive 只参考 planning 完成后的最终输出"的降级设计，Reactive+Planning 在 8k/4k 为 0.31 / 0.26，高于纯 planning 0.25 / 0.05 与纯 reactive 0.12；在 32k/16k 与 planning 持平（0.92 / 0.70）。Gemini 内置思考预算控制超出预算的比例为 4k 90.0%、8k 33.5%、16k 6.4%、32k 0.0%（Figure 9 p27）。

### 真实时间（wall-clock）实验的结果

- **token-时间线性关系（p10, p30）：** 基于 DeepSeek 官方 API 的全部实验轨迹拟合 α = 0.0473 s/token，β = 334.55 s，R² = 0.9986。注意 β 是每个 episode 约 334 s 的固定开销，论文未分解其来源（prefill、排队、网络等）。
- **Table 2（p10，T_E = 6 分钟 ≈ 8k tokens/step，难度未注明）：** Reactive (V3) / Planning (R1) / AgileThinker = Freeway 0.24 / 0.12 / 0.88；Snake 0.37 / 0.04 / 0.45；Overcooked 0.57 / 0.00 / 0.89。
- **Table 9（p26，DeepSeek-V3.2，350 s/step，Hard）：** Reactive (thinking off) / Planning (thinking on) / AgileThinker = Freeway 0.3665 / 0.0 / 0.7022；Snake 0.3050 / 0.0863 / 0.6013；Overcooked 0.5246 / 0.0 / 0.6675。
- 结论归属：RQ1（负荷/压力效应）、RQ2（T_R 权衡）、显著性检验、同等吞吐对照与所有模型变体比较均来自 token 时间抽象；真实时间实验只验证 AgileThinker 在 8k 等价窗口下的相对优势（Table 2、Table 9）及 token–时间线性性（Figure 10），没有在真实时间下重复负荷/压力扫描或 T_R 扫描。

## 与本项目的关系

对照计划文档第 2、3、6、7 节逐项说明。

### 可直接借用的思想与做法

1. **问题形式化与循环写法（p3 Figure 2）：** `think(timeout=T_E)` + `DEFAULT_ACTION` 的接口抽象可以直接作为我们 Real-time 版本中"推理超时→按统一协议继续当前技能或等待"的参考写法（计划 §6.3 第 5 条）。
2. **认知负荷 × 时间压力二维扫描（p4, p6–7；Figure 1/5）：** 我们计划 §7.2 的"成功率—时间压力曲线"与 §10 的"推理复杂度 × 时间压力二维图"在形式上与之相同，应在相关工作中承认该呈现方式来源于此，并说明我们的轴定义不同（事件响应窗口、截止时间余量 vs tokens/step；原任务依赖/记忆要求 vs 游戏难度因子）。
3. **失败模式的对偶描述（p7）：** "reactive 牺牲决策质量换效率、planning 因过时观测执行过时计划"直接对应我们 RQ1 的假设（快分支易违反长程依赖，慢分支易错过事件窗口）。写作时可引用其游戏域证据作为先验，RQ1 在机器人任务上的验证才是我们的增量。
4. **反应线程预算的设定准则（p9）：** "把反应分支预算设为其自然用量上界"是一个可复用的调参规则，可用于我们快分支短决策的预算选择；但我们的快分支如果用候选打分（Jev 式），自然用量的概念需要换成单次前向的延迟。
5. **计划携带观测时间戳并提示其可能过时（p18）：** 他们的 prompt 已含"Turn t1 = …"与"考虑原策略有多少仍然有效"的指令，相当于我们 §6.3 `observation_version` 的最简版本。我们可以沿用，并在此基础上做显式的 `preconditions` / `expiry_conditions` 检查。
6. **实验方法学：** 8 个环境种子 × 4 个采样种子、按配置种子配对的 t 检验（p7, p24–25），以及"同等吞吐对照"（p29–30）的思路，分别对应我们 §7.3 的可复现性要求与 RQ6 的同预算对照。我们需要把后者从 token 交替升级为真实硬件上的测量。
7. **部分推理轨迹共享有效的证据：** 他们显示即使只参考最终输出（Gemini 降级设计）也有收益（p25–27），而 DeepSeek 主实验共享流式中间轨迹。这与我们 §6.4"首版完整子计划交接、后续探索分阶段发布"的路线相容，但我们的计划强调"避免快分支直接消费尚未完成、可能自我否定的中间推理"——这是与他们相反的设计假设，必须作为消融来验证，而不能直接断言。

### 必须明确区分、不能宣称为新贡献的部分

- **"推理期间环境不暂停"的问题形式化、"快反应 + 慢规划并行"的架构、"认知负荷 × 时间压力"的难度设计**，均已由本文提出并用三款游戏实证（p2–6）。与计划 §2 的"定位边界"一致，我们不得把这三点单独作为贡献。
- **"同一模型的快慢两分支"并非全新：** 他们的 DeepSeek-V3.2 实验就是同一模型的 thinking off / thinking on 两种模式分别充当反应与规划线程（p25–26）。我们的"同模型"主张必须限定在**共享 KV 前缀、同一推理服务内的并行调度**与**机器人闭环**上，而不是"同一组权重跑两个分支"本身。
- **"快线程读取慢线程的中间推理"**是他们相对既有双系统方法的核心区分点（p2, p11）。如果我们的快分支也消费慢分支的中间产物，必须引用并说明差异（我们计划以显式发布的子计划/摘要为主）。
- **token 作为硬件无关时间单位**及其与 wall-clock 的线性验证（p4, p10）是他们的方法论贡献；我们用真实时间不构成对其的否定，只是适用域不同。
- **"同等吞吐下优势来自认知分工而非算力"**（p30）已是他们的结论；我们 RQ6 的贡献应是在真实 GPU 上测量显存/带宽竞争后的同预算对照，而非重复该论断。

### 引用时的措辞注意

- 不要写成"RTRG 只用 token 时间"：他们有 DeepSeek API 的 wall-clock 验证（Table 2、Table 9、Figure 10）。准确表述为"主实验采用 token 时间抽象，并在 6 分钟/350 秒级决策窗口下用 API 做了 wall-clock 验证；其'真实时间'是 agent 侧固定决策窗口，环境每窗口离散推进一步"。

## 可复用资产

以下来自仓库 README、`src/realtimegym/agents/{base,agile}.py`、`src/realtimegym/agile_eval.py`、项目页与 HF 数据集卡片的网页抓取摘要，未在本地运行验证。

**代码结构（仓库）**

- `src/realtimegym/__init__.py`：环境注册；`realtimegym.make(env_id, seed=0, render=False)` 返回 `(env, real_seed, renderer)`，`real_seed` 内嵌认知负荷等级；env_id 如 `Freeway-v0/v1/v2`（v0 easy、v1 medium、v2 hard）。
- `src/realtimegym/environments/`：`base.py`（`BaseEnvironment`）、`freeway.py`、`snake.py`、`overcooked.py`、`render/`；`overcooked_new/` 内嵌 overcooked_ai 改版（含 `script_agent/` 搭档脚本与大量 `.layout` 布局）。
- `src/realtimegym/agents/`：`base.py`（`BaseAgent`）、`reactive.py`、`planning.py`、`agile.py`（`AgileThinker`）。
- `src/realtimegym/prompts/`：`freeway.py/.yaml`、`snake.py/.yaml`、`overcooked.py/.yaml`，提供 `state_to_description(observation, mode)`、`DEFAULT_ACTION`、`ALL_ACTIONS`。
- `src/realtimegym/agile_eval.py`：评测 CLI；`configs/`：DeepSeek-V3.2、Gemini-2.5-Flash/Pro、GPT-5-mini、o3 的示例 YAML（`model`、`api_key`、可选 `url`、`inference_parameters`）；`examples/`：`basic_usage.py`、`custom_agent.py`、`difficulty_levels.py` 等；`tests/`。

**接口（仓库）**

- 环境：`env.reset() -> (obs, done)`；`env.step(action) -> (obs, done, reward, reset)`；obs 为 dict：`state_string`、`game_turn`、`state`。新环境需子类化 `BaseEnvironment` 并实现 `set_seed`、`reset`、`step`、`state_string`、`state_builder`，再在 `__init__.py` 注册。
- Agent：`BaseAgent(prompts, file, time_unit)`，方法 `observe(obs)`、`think(timeout)`、`act()`（返回 `self.action`，初值为 `DEFAULT_ACTION`）、`log(reward, reset)`（每步整体重写一个 CSV）、`resume_from_checkpoint(env, csv)`。`AgileThinker(prompts, file, time_unit, model1_config, model2_config, internal_budget)`；LLM 客户端均为 OpenAI 兼容 chat completions，`reasoning_content` 会被包成 `<think>…</think>`；规划模型可加载 HF tokenizer 以支持 token 级部分输出。
- 时间单位：token 模式下反应推理以 `max_tokens = min(internal_budget, …)` 截断，规划输出按 `budget` 切片释放；seconds 模式下反应流在 `max_time` 处截断并 sleep 到窗口结束，规划流在守护线程 + `queue.Queue` 中持续生成。

**评测脚本（仓库）**

- `agile_eval --time_unit token|seconds --time_pressure 8192 --internal_budget 4096 --game freeway --cognitive_load E|M|H --mode reactive|planning|agile --reactive-model-config … --planning-model-config … --seed_num 8 --repeat_times 4`；或 `--settings freeway_M_8192_agile_4096`（五段式 `game_load_pressure_mode_budget`）。约束：planning 要求 `internal_budget == 0`，reactive/agile 要求 `0 < internal_budget <= time_pressure`。
- 输出目录 `{log_dir}/{setting}_{时间戳}/`，每次运行一个 `{repeat}_{seed}.csv`（列含 `state_string`、`action`、`reward`，token 模式另有 `plan`、`model1/2_prompt`、`model1/2_response`、`model1/2_token_num`），`args.log` 记录参数与每次运行的 `reward`、`total_time`；`--save_trajectory_gifs` 可导出 GIF；所有待运行实例以 `ProcessPoolExecutor` 每实例一个进程并行，无并发上限；脚本只报告原始 `env.reward`，归一化需按 Table 4 自行计算。
- 未实现项：C.5 的交替推理（concurrent）模式不在该脚本中。

**数据（HF 数据集卡片）**

- 约 697 MB，MIT；每个 JSON 文件是一次运行的逐步记录，命名 `{game}_{load}_{budget}_{seed}_{agent}.json`（game ∈ freeway/snake/overcooked，load ∈ easy/medium/hard，budget ∈ 4k/8k/16k/32k，seed0–seed7，agent ∈ reactive/planning/agile）。每步字段：`step`、`score`、`thinking`（推理文本）、`state`（随游戏不同）、`action`、`original_state`（输入状态文本）。
- 注意：数据集 viewer 因各游戏 schema 不一致而报错，卡片建议直接读 JSON；卡片示例代码引用的 repo ID 为 `BLeaves/real-time-reasoning`，与页面 `SALT-NLP/RealtimeGym` 不一致，使用前需核实。这些轨迹可用于分析"反应线程何时采纳/偏离规划指导"，但没有标注过时与否。

**能否接入机器人仿真**

- 环境侧：`BaseEnvironment` 是同步、离散步进接口，环境只在 `think` 返回后推进一步，不存在独立运行的仿真时钟；seconds 模式的"实时"由 agent 侧 sleep 实现。要满足计划 §7.1"仿真按 wall-clock 持续推进、推理与技能执行异步"，不能只做一个 LIBERO 的 `BaseEnvironment` 子类，必须自建异步循环与时间戳记账。可借用的是其"固定决策窗口 + 默认动作"抽象作为我们的一个对照条件（离散窗口版本）。
- Agent 侧：`AgileThinker` 的两线程结构、时间预算记账、`\boxed{}` 解析与兜底、CSV 日志可作为我们决策层基线（"同模型并行，不共享前缀"）的参考实现；但它只接受文本状态，接 VLM 图像输入、候选打分式快分支、KV 共享均需重写。token 模式的规划"切片释放"不适用于真实并行测量。
- 模型侧：仅支持 OpenAI 兼容 API；没有本地推理服务（vLLM/SGLang）集成，无法直接用于我们 §6.2 的 KV 共享实验。

## 局限与注意点

1. **token 时间抽象的边界（p4）：** 假设 prefill 可忽略、解码延迟恒定。对 VLM 图像输入与我们强调的观测刷新成本，prefill 并不可忽略；拟合出的 β = 334.55 s/episode 固定开销也未被分解（p10）。线性拟合是 episode 级总量，不代表每步延迟的方差。
2. **离散瞬时动作与无视觉：** 动作瞬时生效、每步一个动作、无中断、无执行失败；观测是完整文本状态（Overcooked 完全可观测，p15）。与机器人闭环差距显著。
3. **主实验仅 DeepSeek（p11）：** 作者说明开源模型总体表现差、商业模型不开放推理轨迹；Gemini 只能跑降级设计（p25）。结论的模型泛化性有限。
4. **并行是模拟的（仓库）：** token 模式下规划输出先整段生成再切片释放，两线程零干扰；真实并行只在 seconds 模式与 Table 2/9 的 API 实验中出现，而 API 吞吐并不暴露硬件竞争。C.5 的"同等吞吐"是 token 交替近似。
5. **并非处处最优：** Easy 下 Reactive (V3) 高于 AgileThinker（Freeway 0.9775 vs 0.9551，Snake 0.7694 vs 0.6931，p23）；32k 下 Planning (R1) 在 Snake 高于 AgileThinker（0.9629 vs 0.8281），Overcooked 16k 为 1.0000 vs 0.9375（p24）；V3.2 Hard/4k 下 AgileThinker 在 Freeway、Overcooked 低于纯 reactive（p26）。结论"consistently outperforms all baselines"（p11）应理解为"在中高负荷与中高压力下"。
6. **T_R 需按环境调参（p9）：** 最优反应预算 Freeway 约 5k、Snake/Overcooked 约 2k，没有自动确定机制。
7. **缺少关键消融：** 没有同一模型下"共享部分推理轨迹 vs 只共享最终计划"的对照（Gemini 降级设计是另一个模型）；没有量化指导过时的频率、反应线程采纳/拒绝的比例。
8. **时间尺度：** wall-clock 实验每步 6 分钟（p10）或 350 秒（p26），与机器人亚秒级决策相差两到三个数量级；结论向机器人场景外推需谨慎。
9. **任务本身的特性：** Freeway 有 BFS 即可求解（code-policy 32k 达 0.9438，p24, p28）；Overcooked 搭档是简单脚本（p15）；Snake 的归一化上限只有 15 个苹果（p15），各方法绝对分数都不高。
10. **文本不一致处（引用时避免照抄）：** 正文引用"Figure 11"但附录只有 Table 11（p29–30）；Figure 6 标题写"Guided by the reasoning of Reactive Thread, Planning Thread … anticipates the trap"，与正文中 R 参考 P 的描述相反，疑为笔误（p8）；R² 在正文为 0.9986、图中为 0.999（p10, p30）；§5 正文说 N_{T_R} 从 0.5k 扫到 8k，Figure 7 横轴仅到 6k/4k（p9）；Table 2 未注明难度等级（p10）。
11. **跨模型比较不公平（p5）：** 作者自述 gym 用于固定模型族内比较 agent 设计，不同 tokenizer 下的 token 预算不可比。我们若混用 API 模型与开源模型，需换算到真实时间。
