## 一句话总结

Robotouille 是一个基于 JSON 定义、离散回合制的 2D 厨房模拟器，把"异步规划"形式化为**带延时效果的 MDP**（动作触发倒计时 timer，timer 随环境步推进），提供同步/异步/多智能体 3 个数据集（各 10 个任务 × 10 个程序生成实例），实验显示 gpt-4o ReAct 在同步任务上成功率 47%、异步任务上仅 11%，主要失败来自规则违反与目标误解而非时间推理本身 (p.1, p.5, p.8)。

## 问题设定与动机

- 作者定义的**异步规划（asynchronous planning）**："the ability to efficiently reason and plan over states and actions that must happen in parallel or sequentially" (p.1)。它面向三类挑战：(1) **time delays**（如煮意面需等待，高效 agent 应趁机做别的事）；(2) **diverse long-horizon tasks**（多目标、动作间依赖）；(3) **multiple agents**（协作与任务分配）(p.1)。
- 作者对已有基准的批评 (p.1, Table 1 p.3)：AsyncHow 评测异步规划但**不是交互环境**，不支持闭环 agent；ALFWorld / WebShop / PlanBench 长程但单 agent 且**无时间延迟**；VirtualHome 有多 agent 与程序生成但无时间延迟；Overcooked-AI 有时间延迟但只有 1 个任务、无高层动作、不面向 LLM。Robotouille 自称同时具备 High-Level Actions、Multi-agent、Procedural Level Generation、Time Delays，30 个任务，最长规划 horizon 82 步 (Table 1, p.3)。
- 三项贡献 (p.2)：(1) 新环境；(2) 3 个数据集，"each containing 10 unique tasks each with 10 procedurally generated instances"；(3) 多个 LLM 基线及定量/定性失败分析。多智能体数据集仅提供，**论文未报告其实验结果**（"leaving multi-agent for future work", p.2）。

## 核心设计

### 环境表示：PDDL 风格的 JSON 域/问题 + "special effects"

- 形式化为 MDP with time-delayed effects，M = <S, A, T, R> (p.2)。状态 s = (ŝ_t, H_t)：ŝ_t 为可观测谓词集合（如 `iscut(lettuce1)`、`on(lettuce1, table2)`）；H_t 为 **timer 变量集合**，每个 timer 由动作创建，倒计时函数 h(x) = d − (x − i)，d 为延迟常数，i 为激活步 (p.2)。
- 转移：动作有谓词前提，无效动作返回原状态；有效动作步中，到期 timer 的谓词并入状态并被移除，新动作可添加新 timer (p.2)。奖励 R: S → {0,1}，仅目标状态为 1 (p.3)。
- 实现上**不是 PDDL 文本**而是 JSON："inspired by PDDL" (p.3)。域 JSON `domain/robotouille.json`：`object_types`（station, item, player, container, meal 共 5 类）、42 个 `predicate_defs`（每个带 `language_descriptors`，用于生成自然语言观测）、15 个 `action_defs`（move, pick-up-item, place-item, pick-up-container, place-container, cook, cut, fry, fill-pot, boil-water, add-to, fill-bowl, stack, unstack, wait）。问题/环境 JSON 在 `environments/env_generator/examples/`。
- 仓库中仍保留 PDDLGym 路径（`pddlgym/`、`utils/robotouille_wrapper.py`、`environments/robotouille.pddl`），但 README 标注 "Currently broken (#37)"；当前主干是 `backend/` 下自研的 `State`/`Action`/`Predicate` 实现。
- **Special effects**（扩展 PDDL 即时效果的"自定义代码块"，p.3）：`backend/special_effects/` 有 5 种：`conditional`（条件满足时施加效果，不满足时取反）、`delayed`（经过 goal_time 步后施加）、`repetitive`（动作重复 N 次后施加，用于切菜）、`creation`（生成新对象，如灌水生成 `water` meal）、`deletion`。`cook` 的定义为 conditional(`item_on(i1,s1)`) → 立即 `iscooking=true` → 嵌套 delayed → `iscooked=true, iscooking=false` (Figure 2c, p.4；源码 `domain/robotouille.json` cook 段)。`fry`、`fill-pot`（delayed → creation water）、`boil-water`（delayed → `isboiling`）同理。

### "异步"的精确含义（最关键）

- **时间 = 离散环境步。** 每个 `env.step()` 为 1 步，所有动作（含 `move` 不论距离、含 `wait` = "Do nothing"）都恰好占 1 步。延迟只以"步数"计：`DelayedEffect.update()` 在每个环境步被动调用一次，`current_time += 1`，等于 `goal_time` 时施加效果（`backend/special_effects/delayed_effect.py`）。`goal_time` 来自环境 JSON `config`（`cook_time`/`num_cuts` 等，`domain/domain_builder.py` 中映射 cut→`num_cuts`、cook→`cook_time`、fry→`fry_time`、boil→`boil_time`、fill→`fill_time`），否则用代码默认 `default_goal_time=4`。30 个数据集 JSON 全部设 `cook_time: 3`、`num_cuts: 3`，未设 fry/boil/fill 时间（按源码推断取默认 4 步，未运行验证）。
- **timer 推进只发生在 `State.step()` 内**（`backend/state.py`）：先对每个玩家执行动作（即时效果 + 把 special effect 注册进 `state.special_effects`，当步 `active=True` 不计时），再对所有 special effects 做一次被动 `update`，然后检查目标、轮换 `current_player`。
- **agent 推理不占用环境时间。** 主循环 `robotouille/robotouille_simulator.py::run_robotouille` 是严格串行的：`agent.propose_actions(obs, env)`（阻塞式 LLM 调用，可多轮重试格式/无效动作）→ `env.step(actions)` → `steps += 1`。LLM 思考多久、重试多少次，世界都**冻结**不动；timer 只因 agent 显式执行动作（包括 `wait`）而推进。因此论文所说的"异步"指的是**任务层面的并发调度**（把耗时工序先启动、同时去做别的子任务），而不是推理与世界并行。
- 从源码看 `ConditionalEffect.update()`：若条件（物品仍在该灶台上）不再满足，只是把 `iscooking` 取反并返回，不更新嵌套 timer；因此把物品拿走会**暂停**而非重置烹饪计时，放回同一灶台后恢复（代码阅读结论，未运行验证；论文未描述此细节）。
- 复杂度论证 (A.9, p.28)：同步 d=0 时搜索空间 O(|S|+|A|)；异步 d>0 时 "O(|S| × (d+1)^n + |A|)，n 为 timer 数"。
- 多智能体：`State.step(actions)` 接受全体玩家的动作列表；`run_robotouille` 只给 `current_player` 赋动作、其余为 `None`，即**回合制**。论文称还支持 "real-time, where an LLM agent controls all agents simultaneously" 和 "networked multi-agent" (p.3)，但在 `release` 分支中**未找到**对应实现（grep real-time/networked/socket 无结果）。

### 任务数据集生成

- 程序生成器 `environments/env_generator/procedural_generator.py`：以问题 JSON 为"达成目标所需的最小对象集"，打乱物品位置、增加新物品/工作站（"shuffles existing objects and adds new objects", p.3）；可选 `noisy_randomization` 保持原解可行。注意 env_generator README 承认工作站位置随机"只是渲染差异"，因为**没有距离度量**。
- 目标用谓词 + `ids` 的组合语言描述，"captures a combinatorial number of goal states that may satisfy a vague language goal" (p.3)；`build_goal()` 展开成析取式。
- 实例化方式：Hydra 配置 `conf/evaluation/*.yaml` 中 `testing_seeds: [42, 84, 126, 168, 210, 252, 294, 336, 378, 420]`，即每任务 10 个种子 = 10 个实例。训练用 in-context 示例来自单独的 `synchronous_train/0_cheese_onion_sandwich` 与 `asynchronous_train/0_chicken_onion_sandwich`（排除在测试集之外，p.5）。

### 观测与动作接口

- 观测是**纯文本**（`robotouille/env.py::LanguageSpace.state_to_language_description`）：按对象列出所有为真的谓词的自然语言描述（如 "chicken2 is cooking"、"stove4 has nothing on it"），再附 "Valid Actions:" 完整合法动作列表与 "Goal: <自然语言目标>"。**timer 剩余时间不在观测中**，agent 只能看到 `iscooking`/`iscooked` 等二值谓词。`observation_space = action_space = LanguageSpace`（最长 32768 字符）。
- 动作是自然语言模板字符串（如 "Cook {i1} on {s1} using {p1}"、"Do nothing"），由 `State.get_valid_actions_and_str()` 枚举；ReAct agent 用正则取 "Action:" 并与合法列表精确匹配，不匹配则回传 "Error Feedback" 重试（最多 `max_feedback_steps=5` 次，累计超过 `feedback_attempts=3` 轮则终止）。
- 渲染：pygame，`render_mode` human / rgb_array，可录视频；图像不作为 agent 输入。

### 成功判定

- "Success rate is determined by reaching the goal within 1.5 times the optimal number of steps for the given instance. Baselines exceeding this step limit are terminated." (p.5)。代码中 `max_step_multiplier: 1.5`，`optimal_steps` 按任务硬编码（agents/README 承认是基于 seed=null 的默认环境，而非每个实例单独计算，与论文"for the given instance"的表述略有出入）。
- 目标达成即 `done`；`RobotouilleEnv.step` 返回的 reward 恒为 0，成功仅看 `done`。无部分完成分、无违规惩罚、无时限以外的时间指标。
- 另报 optimality rate = ‖τ̂‖/‖τ*‖ (p.6) 与失败时的 normalized steps-to-go = ‖τ*_left‖/‖τ*‖ (p.7)，均基于步数。

## 实验与主要结果

### 模型与基线 (Section 4.1, p.5)

- 模型：gpt-4o、gpt-4o-mini、gemini-1.5-flash、claude-3-haiku；temperature 0.7；每个基线 1 个 in-context 示例。README 排行榜另列 Qwen2-72B/32B-Instruct、Llama-3.1-70B/8B（ReAct 同步 7/6/2/1%，异步 2/1/0/0%），**这些数字不在论文中**。
- 基线：`I/O`（给初始状态+合法动作+目标，一次性输出整个计划，开环）；`I/O CoT`（每步前有估计结果状态的思维链，开环）；`ReAct`（闭环，每步输出 Reasoning+Action 并接收新状态；使用只保留上一步 reasoning/action 的消融版 "last-reasoning-action-mpc"，A.7 Table 4 p.27：9 题中解 3 题、平均 28.33 步、$2.64，与保留上一步观测的版本并列最好但更便宜）。附录另有 PLaG (BaG) 与 Reflexion (A.15)。

- A.16 (p.35, Table 7)：把异步 Task 1–3 的 delay 设为 0 变成同步版本后，成功率 20/30/40 → 50/60/50，直接证明时间延迟本身增加了难度。

### 失败模式分析要点

- 两种设定失败模式高度相似，都是规则违反与目标误解 (p.5, p.8)；作者据此主张改进方向是**长程反馈整合**与**自我审计**（self-verification），而非专门的时间推理 (p.10)。
- 定性案例 (A.10–A.12, p.28–33)：误以为灶台上的肉已熟（State）；反复提出不存在的 "Transfer" 动作（Action）；在一块砧板上叠放两颗洋葱一起切（Transition）；汉堡顺序/漏掉预处理步骤（Goal）；灶台被占时按规则反复拿起又放下（A.11）。
- Discussion (p.10)："Real-World Application" 段承认 LLM 的成本与**推理时间**必须降低，且随上下文增长而增长，但论文本身**没有测量任何 wall-clock 推理耗时**，也未把它与环境时间挂钩。

## 与本项目的关系

对照计划文档第 2 节（Robotouille 行："厨房长程规划、动作依赖、耗时与异步调度" → 需补 "区分任务并发与真实推理延迟，验证持续演化的物理闭环"）、5.1 节（可选：复用 "工序依赖、并行任务和可配置状态转移"，新增 "将实际推理耗时接入环境时钟"，定位 "轻量算法调试，不替代机械臂验证"）、5.5 节（E1–E5 事件）与 6.3 节（计划版本与有效性检查）。

### 本质区别：Robotouille 的"异步" vs 本项目的"真实推理延迟接入环境时钟"

| 维度 | Robotouille（论文/代码事实） | 本项目需要的 |
| --- | --- | --- |
| 时间单位 | 离散环境步，每动作 1 步，timer 按步倒计时 | wall-clock 持续推进，仿真/真实时间 1:1（计划 7.1） |
| 推理期间世界是否变化 | **不变**：主循环串行，LLM 调用期间状态冻结 | 必须变化：推理与技能执行重叠 |
| "异步"指什么 | agent 对**任务内部并发**的调度（先开火再切菜） | 推理过程与世界演化的异步 |
| 计划过时问题 | 不存在：观测与动作之间世界不可能变 | 核心问题（6.3 计划版本、前提检查） |
| 等待的代价 | 只消耗步数预算（1.5× 最优），无负面后果（不会烧焦、无截止期） | 等待需能改变可执行动作/约束/结果（5.3："只添加计时器不足以测试实时判断"） |
| 外生事件 | 无（仅可选的"切菜回退"抽象扰动） | E1–E5 可观测事件 |
| 时间信息可观测性 | 只有二值谓词（is cooking / is cooked），无剩余时间 | 需明确观测采样/生效时间戳 |
| 底层执行 | 符号瞬时成功，无失败、无中断语义 | 技能耗时、可失败、明确中断语义（4.1） |

结论：按本项目 7.1 的三类条件，原版 Robotouille 在构造上就是"**暂停环境参考**"条件，且连"推理等待损失"都为零。它测的是"模型能否想出一个好的并发调度"，不是"模型想的时候世界会不会跑掉"。计划文档第 2 节的定位表述是准确的；引用时不要把它说成实时或延迟基准。另注意计划文档第 2 节已提醒：PACE 使用的是 Robotouille **同步**任务子集加参数化动作耗时，与原基准的 timer 模型和我们的物理闭环都要区分。

### 最小改动：把真实 wall-clock 推理耗时接入其时钟（作为轻量调试环境）

以下为基于源码阅读的改造建议，均未实现验证：

1. **把推理耗时折算为环境步并"补跑"**（最小改动，约几十行，只改 `run_robotouille`）：
   - 在 `agent.propose_actions(obs, env)` 前后用 `time.monotonic()` 计时得 Δt；设定 `seconds_per_step`（如 1–3 s，作为时间压力旋钮）；k = round(Δt / seconds_per_step)。
   - 在应用 agent 动作之前，对环境执行 k 次 `wait`（`env.step([(wait_action, {}), ...])`），让所有 timer 推进 k 步；并把 k 计入 `steps`，使思考消耗步数预算。
   - 此时 agent 看到的观测已过时 k 步：必须用 `env.current_state.get_valid_actions_and_str()` **重新校验**动作是否仍合法（这正是 6.3 第 4 步的"基于最新可观测状态检查计划前提"），不合法则记为 "stale action" 并按统一协议处理（丢弃/重规划/继续等待）。
   - 记录每条决策的 `observation_version`、`created_at`、返回时间、生效时间（7.1 时间戳要求）。
   - 优点：完全复用 `State`/timer 机制、评测脚本与日志；缺点：仍是离散步，仿真不会在 LLM 调用中途推进，属于"延迟折算"而非真正的实时闭环。
2. **真正并发版本**（改动更大）：把 `env.step` 放到固定节拍的时钟线程（每 `seconds_per_step` 自动执行一次 `wait`），agent 在另一线程/异步任务中提交动作到队列；需要处理 `State.step` 的就地修改与线程安全（`RobotouilleEnv.__deepcopy__` 可用于给 agent 拍快照）。这更接近 7.1 的"真实时间闭环"，但 Robotouille 本身没有持续物理过程，收益有限。
3. **让"等待"产生后果**（否则 1、2 只会测出"想得越久、步数越少"）：利用 special effects 机制最少改动域 JSON：
   - 在 `cook`/`fry` 的 delayed 之后再嵌套一个 delayed，设 `isburnt=true`（需新增谓词与渲染资源），形成 **E3 型有期限机会**："煮熟后 k 步内必须取走"。
   - 用第二个 `player` 跑**脚本化规则策略**（`State.step` 已支持多玩家动作列表），在特定步占用灶台、移走物品或改变放置区，形成 **E2 场景状态变化** / **E4 资源不可用**；这是现成接口，不需要新机制。
   - E1 目标更新需要在 `run_robotouille` 中按步或按状态条件替换 `state.goal` 与 `goal_description`（`build_goal` 可复用），并把变更文本注入观测。
   - 现有 `stochastic`（切好的食材回退）是**离散重置型抽象扰动**，若使用应按 5.5 的要求单独标注与报告。

### 哪些任务模板具备"等待会改变可执行动作/约束/结果"的性质

- 原版中**没有**任务让等待带来负面结果；等待只会解锁动作（timer 到期后 `iscooked`/`isboiling`/`water` 出现，使 pick-up/add-to/fill-bowl 变为合法）。因此原版任务只具备该性质的"正向一半"。
- 最适合改造的模板（timer 多、依赖链长）：
  - `asynchronous/5_potato_soup`、`6_onion_soup`：fill-pot → boil-water 两段串行 timer + 切菜 + 盛碗，是最短的"多 timer"任务（最优 19/42 步），适合作为 E3（煮沸后限时盛出）和 E5（有限暂存）的调试模板。
  - `asynchronous/3_tomato_burger_and_fries`、`4_onion_cheese_burger_and_fried_onion`：stove + fryer + board 三种工作站并行，适合 E4（某工作站临时不可用需重排）。
  - `asynchronous/7`–`9`：汤 + 多份三明治/汉堡，gpt-4o 全部 0%，适合作为"推理复杂度"高档位，但基线已饱和于 0，需先确认可解性（5.6 的要求）。
  - `multi_agent/*`：两玩家、共享 stove/board/sink，天然适合把第二玩家改为脚本化扰动源。
- 同步数据集（无 timer）可作为 5.3 中的"无事件对照"，但要注意它连 timer 都没有，不等于"Original 版本"的实时对照。

### 引用时的措辞注意

- 写成 "an asynchronous *planning* benchmark with time-delayed action effects in a turn-based, discrete-step simulator"；不要写成 real-time、wall-clock、latency benchmark。可引用其 MDP 定义 (p.2) 说明其 timer 以环境步计。
- 47% / 11% 是 gpt-4o ReAct、1.5× 最优步数预算、单个 in-context 示例、temperature 0.7 下的成功率，包含次优成功 (p.5–7)。
- "30 tasks" = 同步 10 + 异步 10 + 多智能体 10，每任务 10 个程序生成实例；多智能体部分论文无结果。
- 论文声称支持 real-time 与 networked multi-agent (p.1, p.3)，但 release 分支代码中未见；引用该功能时写"作者声称"。
- 作者自己的结论是失败主要来自规则违反和目标误解、需要更好的反馈整合与自我验证 (p.5, p.10)，不是"LLM 不会时间推理"；不要过度解读为时间压力导致失败。
- 会议信息以 README bibtex（ICLR 2025）为准；arXiv v1 日期 2025-02-06。

### 环境配置文件格式（`environments/env_generator/README.md`）

- 顶层字段：`version`, `width`, `height`, `config{num_cuts{item|default}, cook_time{item|default}, ...}`, `stations[{name,x,y,predicates?,id?}]`, `items[{name,x,y,stack-level,predicates?,id?}]`, `containers[]`, `meals[]`, `players[{name,x,y,direction}]`, `goal_description`, `goal[{predicate,args,ids}]`。
- `ids` 用整数表示"同类对象中的同一个/不同个"，用字母表示"必须是某个具体对象"（对应 Figure 2d, p.4；Figure 8, p.15）。
- 示例 `asynchronous/5_potato_soup.json`：6×6，stations = table×3 + stove + board + sink，items = potato，containers = pot + bowl，goal = `in(water,bowl)`, `addedto(potato,water)`, `isboiling(water)`, `container_at(bowl,table)`。

### 自定义任务与事件

- 新任务：在 `examples/` 加 JSON 即可；`python main.py ++game.environment_name=<name> ++game.seed=<seed>` 生成实例。
- 新动作/新状态转移：改 `domain/robotouille.json` 的 `predicate_defs`/`action_defs`（含 `precons`、`immediate_fx`、嵌套 `sfx`），渲染需在 `renderer/configuration` 的 rendering JSON 加图标 (Figure 9, p.16)，人类操作需改 `domain/input.json` (Figure 10, p.16)。
- 可配置延迟：`config` 中的 `cook_time`/`fry_time`/`boil_time`/`fill_time`/`num_cuts`（按 `domain_builder.py` 映射；release 提交 #71 刚加入 goal_time 可定制）。
- 事件机制：**原版没有**独立于动作的事件/调度器；最省力的事件源是多玩家接口（脚本化第二玩家）和在 `run_robotouille` 主循环中按步插入状态修改（`stochastic` 代码块就是这样做的）。

### agent 接口

- 继承 `agents/agent.py::Agent`，实现 `propose_actions(obs: str, env) -> List[(Action, param_arg_dict)]`（可一次返回多步，主循环会按队列执行）、`is_done()`、`is_retry(steps_left)`；在 `agents/__init__.py::NAME_TO_AGENT` 注册；用 `env.current_state.get_valid_actions_and_str()` 把字符串映射为可执行动作。
- LLM 调用层 `agents/prompt_builder/prompt_llm.py` 支持 OpenAI / Anthropic / Google / HuggingFace pipeline（见 `requirements.txt` 与 `conf/llm/base_llm.yaml` 的 `max_length: 8192`），prompt 以 `experiment_name/prompt_description/prompt_version` 版本化（如 `prompts/ReAct/1.3.1-last-reasoning-action-mpc.yml`，含环境规则与"食谱指南"）。
- 评测输出：`results.json` 含每个 `<env>_<seed>` 的 `done/steps/max_steps`、总体 `accuracy`、`average_steps`；LLM 交互日志 `log_*.txt`；可选 mp4。
- 一键复现：`python main.py +experiments=ReAct/asynchronous/last-reasoning-action-mpc`（agents/README.md）。

## 局限与注意点

1. **推理零成本、世界冻结**：这是对本项目最根本的限制（见上）。所有"时间"结论都是关于步数效率的。
2. **动作粒度过粗**：`move` 不论距离 1 步、无运动/碰撞/失败/中断语义；`wait` 也是 1 步。不能作为机械臂物理能力或底层控制的证据（计划文档 9 节后续扩展原则已写明）。
3. **timer 不可观测**：agent 看不到剩余时间，只能靠规则先验推断；这与我们"带时间戳观测"的设定不同，也使"等待多久"的决策变成猜测。
4. **等待无惩罚、无外生事件、确定性**：原版不会出现"旧计划失效"；若用于调试 6.3 的计划检查逻辑，必须先加事件。
5. **成功判定与最优步数**：论文说按实例的 1.5× 最优步数 (p.5)，代码按任务硬编码默认环境的最优步数（agents/README 明说，BFS 太慢 #38）；程序生成实例的最优步数可能不同，评测口径略有偏差。
6. **样本量小、方差大**：每数据集 100 局；A.8 (p.28) 给出 Task 2/3 为 30.0 ± 13.8 与 40.0 ± 14.8；Finding 7 自认不显著。
7. **少样本示例质量是混杂变量**（A.8, p.27–28）：单个 in-context 示例决定了哪些任务"在分布内"，horizon 与成功率不单调。
8. **多智能体部分无结果、real-time/networked 代码未见**；多智能体 JSON 全为 2 玩家。
9. **论文与代码的小不一致**：随机扰动概率（33% vs 0.1）、Table 5 Total 行、A.14 的 58.5% 与 Finding 4 的 56.8%。引用数字时注明出处。
10. **观测为长文本**：对象多时观测很长（上限 32768 字符），长程任务成本高（A.7 单次小规模消融 9 局 $2–3）；这也是作者在 Discussion 中提到的部署障碍 (p.10)。
11. **PDDLGym 路径已损坏**、BFS 规划器过慢：不要指望用它做诊断 oracle，需要自写规划器或用 Fast Downward 翻译（`pddlgym/downward_translate` 存在但未验证）。
12. 作者的失败归因（规则违反、目标误解）提醒我们：在加入实时要素后，要能把"规则/语义错误"与"延迟/过时错误"分开计数（计划 7.2 的失败分类），否则会重复 Robotouille 的结论而测不到实时判断。
