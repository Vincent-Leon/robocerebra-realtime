## E0.1 冒烟测试与仿真吞吐（`e01_smoke_and_speed.py`，Ideal/case1）

- 环境创建 15.3 s，reset 2.6 s；macOS 离屏渲染正常（agentview / eye-in-hand 256×256，见 `exp/runs/e01/Ideal_case1/*.png`）。
- 官方 `init_files` 的状态与 `demo.hdf5` 第 0 帧**完全相同**（max |Δ| = 0）。
- 观测含特权量：每个物体的 `*_pos/_quat`、`object-state`（56 维）、`robot0_proprio-state`（39 维）。辅助赛道的"结构化可观测状态"可直接取自这些键；主赛道需屏蔽。

| 测量 | 结果 |
|---|---|
| env.step（物理 + 2 相机渲染） | 均值 27.9 ms，p50 13.2 ms，p95 14.9 ms → 约 36 步/s |
| env.step（仅物理） | 5.5 ms → 182 步/s |
| `_check_success` | 0.24 ms/次 |
| 控制周期 | 20 Hz（dt = 50 ms） |

结论：**仿真侧在本机支持 1:1 实时（RTR = 1）且有约 50% 余量**；决策模型须放在独立进程/远程 API，否则会抢占仿真线程。

## E0.4 脚本化抓放执行器试运行（`skills.py` + `e04_scripted_pickplace.py`）

执行器：特权状态（物体位姿、区域站点）+ OSC_POSE 比例控制，三段式运动（抬到安全高度 0.70 m → 水平移动 → 垂直下降），停滞检测（12 步位移 < 2 mm 视为被挡），放置时被挡但距目标 ≤ 12 cm 则低处松手。每步调用一次官方监控器并记录时间戳，支持取消标志（为异步版本预留）。

| 任务 | 结果 | 技能明细（步数 @20 Hz） | 备注 |
|---|---|---|---|
| Ideal/case1 | 4/6（与演示 oracle 相同） | pick 81 / place 111 ✗ / pick 112 / place 124 ✓ / pick 101 / place 86 ✗ | 3 个 pick 全部成功且被监控器判定；放置失败一次是谓词（bottom_side）未触发，一次是搬运停滞（可能撞到已放入的物体） |
| Ideal/case2 | 2/4 | pick 75 / place(top_side) 90 ✓ / pick(frypan) ✗ / place(rack_1) ✗ | 平底锅按几何中心抓取被锅体挡住（需抓手柄）；`rack_1` 是物体不是站点，需按物体顶面放置 |

- 整条 case1 轨迹 630 步 = 31.5 s 仿真时间，wall-clock 9.3 s（约 68 步/s，无渲染）。**脚本执行器单个技能约 80–120 步（4–6 s），比人类演示（250–500 步）快 2–4 倍，比官方 150 步/子步预算略快**，适合作为固定执行器，并可用 `max_speed` 调速制造时间压力。
- 第一版（无三段式运动）在 z≈0.55 水平搬运时撞到储物盒侧壁（盒顶 ≈0.60），说明安全高度必须按目标固定装置顶面计算。
- 视频：`exp/runs/e04/Ideal_case1/rollout.mp4`，关键帧 `frames_grid.png`。

**失败原因分类（`x_pick_diag.py` 对 Ideal/case2、case4、Memory_Execution/case1、Mix/case7 的诊断）**：

| 类别 | 例子 | 性质 |
|---|---|---|
| A. 目标区域语义与几何不符 | case1 `in → right_side/left_side`（4 mm 侧壁）、case2 `in → top_side`（演示放进盒内被判为 bottom_side） | 标注/goal.json 问题，可通过"映射为盒内任意区域"修复 |
| B. 谓词类型与演示行为不符 | case4 任务文本"把两个盒子放进碗里"，goal 写成 `pour`（要求 40 帧内四元数变化 > 0.2），演示是平放进去 | goal.json 生成错误 |
| C. 物体初始不在任何受监控区域 | Memory_Execution/case1 `pick milk_1`：milk 起始 regions=[]，而 `pick` 要求"从非空区域集变为空" | 监控器结构性缺陷，该物体的 pick 及其后续全部级联失败 |
| D. 四元数抑制过严 | case2 `pick frypan`：抬起时 Δquat=0.32 > 0.1 被判"pick suppressed" | 监控器阈值问题（对带柄物体尤甚） |
| E. `on rack_1` / `open <抽屉区域>` 谓词几何 | 演示把 butter 放到架上仍只判为 in 桌面；人类开抽屉后 open 不触发 | 需逐个核对 LIBERO 谓词实现（下一步） |
| F. 级联 | 任一前序子目标未触发 → 同一物体后续子目标不再评估 | 放大 A–E 的影响 |

含义：
- **原基准报告的绝对成功率（GT-plan 25.2% / Ideal 31.2%）有一部分是判定器造成的上限损失**，不全是模型能力。引用时应说明；比较不同方法仍可用相对差异。
- 对本项目：改造版本必须**只在 oracle 可验证的子目标上计分**，或在明确记录的前提下修复 goal 规范（A/B 类）与监控器（C/D 类），并用 E0.5 的回放重新验证。计划文档 §5.2"改造后的分数不能直接当作原 benchmark 排行榜成绩"正好覆盖这一点。

## E1.0 实时异步环境原型（`realtime_env.py`、`e10_realtime_demo.py`、`plot_timeline.py`）

设计：仿真在主线程按 wall-clock 推进（每控制步对齐到 t0 + k·dt/RTR，macOS 离屏渲染需主线程 GL 上下文）；规划器在工作线程读取带版本号的观测快照、经命令队列提交技能或取消；技能在仿真线程内逐步执行，每步检查取消标志；记录观测采样 / 命令提交 / 技能开始·结束·取消 / 子目标完成 / 规划器自报思考区间的时间戳，以及实际 RTR 与每步滞后。

演示（Ideal/case1，伪规划器每步"思考" 3 s，第 2 个技能执行 1.5 s 后取消再重发）：

| 指标 | 结果 |
|---|---|
| wall-clock / 仿真时间 | 61.4 s / 57.5 s（含 15 步静置） |
| 实际 RTR | **1.000**（每步滞后 p50 = p95 = 0 ms） |
| 思考 3 s 期间世界推进 | 59 控制步 ≈ 2.95 s |
| 取消延迟 | 请求于 step 262，技能于 step 263 终止（1 个控制步 = 50 ms） |

## E2.0 第一次事件实验暴露的两个问题（已修复，结果作废）

## 方法原型：同模型快慢双分支（`exp/run_dual_episode.py`、`exp/dual_planner.py`）

同一模型 sal-pro：慢分支 = 开启思考，生成**剩余完整计划**（带 plan_id、观测版本、生成时消息数）；快分支 = 关闭思考，三种用途：
1. **兜底决策**：没有可执行的计划步骤时（开局、慢分支思考中、计划被判失效）直接给出下一步，让机器人不空等；
2. **语义检查**：计划生成后又出现了新消息时，对下一步判断 execute / skip / wait_for_replan；
3. **执行中监控**：技能执行期间到达新消息，判断是否取消当前技能。

协调器：逐步执行计划，执行前做程序化前置条件检查（手是否空、抽屉开度等可观测量）；新计划到达时与"计划观测时刻之后已成功执行的动作"对账，跳过已完成的开头步骤；任何动作成功后若与计划下一步相同则推进游标（防止计划在动作执行中途到达造成重复）；技能失败 / 计划耗尽 / 新消息 → 请求重新规划，思考期间快分支继续推进。

对应计划文档 §8.1 的"同模型并行，不共享前缀"。共享前缀版本需在自部署 vLLM 上实现（E1.2 已证明实验室网关无可控前缀缓存）。

## E2.3 正式对照前发现并修正的四个有效性问题（2026-10-16 晚）

正式对照启动了三次，前两次在发现问题后中止，结果全部归档到 `exp/runs/_discarded/`、`exp/runs/llm_v2_ratelimited/`，不纳入结论。

1. **网关限流（429）**：4 路并行时 18 个 episode 中有 4 个遇到 429（198 次调用中 13 次），双分支把 429 当成"计划无效"立即重试，10 秒内连续 7 次，形成重试风暴。修正：客户端对 429 / 5xx / 连接错误指数退避重试（最多 6 次，等待计入延迟并逐次记录），双分支出错后退避 2 s，并行度降到 2。
2. **执行器 bug**：拿着物体开抽屉时，抽象抽屉技能会张开夹爪使物体掉落。修正：开关抽屉、拧旋钮要求空手，否则立即失败并提示"先放下"。
3. **计分器误给分**（E2 测试中发现）：
   - 倒：官方谓词"40 帧内与容器距离 < 0.3 m 且姿态变化 > 0.2"会把搬运途中的晃动算作倒。改为 **R8**：被倒物体在手中、位于容器上方（水平距离 ≤ 容器半径 + 6 cm、高于容器），且在上方期间姿态变化 > 0.2；放进容器仍算（R2）。
   - 抓取：瞬时抬起一侧（夹盘子未夹住）被算作拿起。改为 **R3'**：靠近末端（阈值 max(0.10 m, 物体包围半径 + 4 cm)，瓶子从瓶颈抓取时原点离末端较远）且抬升 > 4 cm 或离开受监控区域，**连续保持 ≥ 10 帧**。
   - 验证：40 个任务的演示回放结果与 v2 完全相同（36/40 任务、396/405 子目标），即没有误伤真实演示；E2 中未倒成的那次不再给分。
4. **实时性被 CPU 争用破坏**：与实时 episode 同时运行全速 CPU 任务（官方协议批次、oracle 网格，最多 7 个仿真进程）时，部分 episode 的仿真出现 0.5–60 s 的停顿，事后以超实时速度追赶，整局平均 RTR 仍显示 1.000——平均 RTR 掩盖了局部违规。仿真变慢等于免费送给规划器思考时间，追赶则压缩机器人动作时间，都会扭曲时间压力测量。修正：**有效性判据**——每 20 步的滞后最大值 ≤ 0.25 s 且逐步滞后 p95 ≤ 50 ms，否则标记无效并重跑（计划 §7.1）；全速 CPU 任务不再与实时 episode 并发。

## E2.5 第三次正式对照（计分器 v3，69 个 episode，结果仅作行为观察）与随之发现的问题

- **执行器取消后卡住**：快 + 监控有一次取消放置后，后续搬运反复停滞，规划器把同一失败动作重复了 10 次（控制失败 + 决策层不换策略）。

1. **R6 误给分**：桌面判定"高出桌面 ≤ 20 cm"把储物盒里的物体也算作在桌面上，掩盖了"仅快"规划器无视改目标消息的决策失败。改为 **R6'**：不在手中（双指同时接触才算在手中，robosuite `_check_grasp`），且不在任何其他受监控装置区域内。
2. **抽屉区域重叠**：LIBERO 同一柜子的抽屉判定区域在高度上重叠（半高 0.088 m、中心相距 0.043 m），放进上层抽屉也会被判为在中层。新增 **R9**：同一柜子的抽屉区域按高度就近归属。
3. 验证：针对性测试全部正确；40 个任务的演示回放仍为 36/40、396/405（与 v2/v3 相同，未误伤演示）。
4. **计分与执行解耦**：实时环境逐步保存仿真状态（`states.npz`），`exp/rescore.py` 可用任意版本的计分器离线重算（含 E1 目标更新），冒烟测试与在线计分完全一致。今后计分器再改无需重跑。
5. **双分支**：慢分支计划中有非法步骤时整体拒绝并把具体原因反馈给慢分支（此前静默丢弃，产生"只抓不放"的残缺计划）；快分支连续两次宣布完成即结束（此前慢分支长考时会空转到超时）；开局前预热 API 连接。

1. **事件触发的快速检查决定了对目标更新的响应**（E1）：同一模型关闭思考做一次"继续/取消"判断，就把进行中的过时放置在 1–2 s 内取消，有效响应延迟从 18.9 s（仅快，且 3 次中只有 1 次真正响应）/ 89.8 s（仅慢）降到 4.1 s / 6.6 s；整任务成功从 1/3、2/3 提高到 3/3。没有监控时，**仅快规划器 2/3 次直接无视了改目标消息**（过时放置执行完后继续收拾其他物品），这在修正 R6 之前被计分器掩盖。
2. **慢分支最先在时间压力下失效**（E3）：20/12 s 时间窗三种方法都 3/3 按时；9 s 窗仅快 3/3、仅慢 2/3、双分支 2/3；6 s 窗仅快 1/3（余量 0.1 s）、其余 0/3。与诊断 oracle 的可行性边界一致：6 s 窗只在每步决策延迟 ≲ 2–3 s 时可行，而仅快的调用延迟中位数约 2.7 s。
3. **开启思考的延迟呈重尾**：中位数 4–8 s，但在"新消息与当前状态冲突"时出现 80–160 s 的长考，甚至用满 4096 token 返回空内容；这是仅慢在 E1 中响应延迟 89.8 s、完成时间 206 s 的直接原因。
4. **双分支在这些短任务上并未真正用上慢分支**：慢分支第一个计划平均约 30 s 后才返回（16–50 s），145 个执行步骤中只有 16 个（11%）来自慢分支计划，E1 的 3 次运行中慢分支一个计划都没交出。因此双分支的 E1 表现（响应 4.3 s、3/3、完成最快 57.9 s）应归功于快分支的事件监控与语义检查，而不是"快慢协同"。检验慢分支价值需要更长、推理更重的任务（Memory 类）或更快的慢分支（思考预算、自部署前缀缓存）。
5. **case1 无事件基线成功率偏低（1/3–2/3）主要来自执行器与接口**：抓取前未检查手是否为空（拿着奶酪又去抓爆米花，奶酪掉落）、三个盒子都放到 `bottom_side` 同一中心点导致堆叠掉出、接近时停滞后规划器反复 `wait`。这些不是时间推理问题，但会给 case1 的所有方法加入噪声，列入下一轮执行器修正。

## E3.3 缓存友好布局 + Jev 式快分支（`shared_prompt.py`、`jev_fast.py`、`run_dual_shared_episode.py`）

- 所有分支共用同一系统提示，用户消息按"静态块（任务、id、固定区域坐标）→ 只追加的历史 → 当前图像 → 当前状态 → 模式指令"排列；`--cache_bust=on` 在系统提示前加随机串，内容相同但不复用缓存，用于分离共享 KV 的效果。
- Jev 式快分支：程序化列出当前所有合法技能调用（不按任务筛选），模型只生成 1 个 token，读该位置 top_logprobs 中各字母的概率取最大者；事件监控 / 计划检查同样用字母选项。
- 冒烟（E3 9 s 窗，仅快分支 Jev）：每次决策 **0.30–0.39 s**（文本模式约 2.6 s），每次调用命中 1 块 784 token 缓存（约占提示 52%），整任务 6/6、48 s。代价是决策质量：先拿黄油再开抽屉、重复抓取，体现了无推理快分支的典型错误——这正是双分支用慢计划弥补的对象。

| 方法 · 分支 | 延迟 | 提示中命中缓存 |
|---|---|---|
| 文本快分支（关思考） | 2.69 s | 0%（旧布局） |

结论：
1. **快分支的瓶颈是解码而不是预填充**：文本快分支即使首 token 只要 0.44 s，生成约 50 token 的 JSON 仍需约 2.9 s。Jev 式候选打分只生成 1 个 token，决策降到 0.4 s，把 E1 有效响应从约 4.5 s 降到 0.8 s，使 E3 6 s 窗从不可行（0/3）变为 3/3——与诊断 oracle 的可行性边界一致（6 s 窗要求每步决策 ≲ 2 s）。
2. **共享 KV 的单独贡献**（同内容、禁缓存对照）：Jev 决策延迟 0.69 → 0.42 s（−39%），对慢分支首 token 只有约 0.1 s 改善（慢分支由解码主导）。当前静态前缀只能凑满 1 块（784 token），更长的稳定前缀（记忆任务的历史）收益会更大。
3. **双分支在这些短任务上仍未超过仅快·Jev，失败来自协调器缺陷**。两次 Jev 失败（w6、w9 的种子 2）逐条核对时间线，机制相同：
   - 慢计划到达前（0–18 s）由 Jev 快分支兜底，决策质量差：连续两次拿起黄油（执行器未禁止"手中有物再抓取"）、向关着的抽屉放置被拒、把黄油放回桌面、再打开抽屉；
   - 慢计划在约 18 s 到达，依据的是开局（0 s）时的观测；对账只按"已执行动作序列"匹配，把"拿起黄油"记为已完成，没有发现黄油已回到桌面；
   - 下一步"放入中层抽屉"前置检查失败（手中无物），协调器请求了重新规划，**但只跳过这一步、继续执行旧计划的剩余步骤**：在黄油仍在桌面时执行了"关中层抽屉"（约 20–24 s），然后去做番茄酱的步骤。约 27 s 警告到来时抽屉已被自己关上，截止时（33.3 / 36.0 s）被事件锁定，新计划要到约 49 s 才到达。（时间均为相对开局，与汇总表一致。）

### E5.2 建议模式：Prompt 注入（组会行动项 1）

- 用法：`run_dual_shared_episode.py --slow=advice`。
- 慢分支**关闭思维链**，以新增的 ADVISE 模式输出至多两句建议（`{"advice": ...}`，上限 120 token）。下一次快分支（Jev）决策时，建议以 `ADVICE from the deliberate planner (given at …; asked because …)` 的形式注入，位置在历史和当前状态之后、模式指令之前，因此"系统提示 + 静态块 + 历史"仍是可缓存的公共前缀。
- 触发条件：开局、技能失败、检测到循环（同一调用连续 3 次，或两个调用交替出现）、新消息；`--advice_every=N` 可另加每 N 个动作的定期刷新。慢分支忙时，请求排队，按最新原因再给一次。

批量中发现的设计缺口（留到下一轮修改，本批用冻结代码不受影响）：快分支第一次选"完成"时会请求慢分支核实，但约 1 s 后第二次选"完成"，episode 就结束了，核实建议来不及到达。case5 两局都这样在 74–97 s 提前收尾，平底锅始终留在抽屉里、没放到灶上（6/14）。建议模式下每次只需 2–3 s，应当等核实建议到达后，再接受第二次"完成"。分析脚本：`exp/analyze_r3.py`。

**补测 r3b：完成须经核实**（`exp_r3bsnap/`，`exp/runs/llm_l20_r3b/`，case5 建议注入 5 局，执行器与 r3 相同）。

快分支首次判"完成"后，等慢分支核实（最多 8 s）再决定。结果：11、12、12、8、12/14，均值 0.79；r3 不加核实时为 0.87，**没有改善**。

- 另外 2 局轨迹不同，暴露两个新的执行器问题：
  - 黄油放进平底锅时掉出，落在离底座 0.80 m 的够不着处。快分支随后连续 14 次抓取失败，直到耗尽 40 次技能上限。慢分支建议"先放到桌上"，对够不着的物体不可行。
  - 慢分支两次建议"把平底锅放到灶上（flat_stove_1）"，但快分支的候选动作里没有灶台目标，只能先选"放到桌面"（大件搬运途中停滞），再选"放到柜顶"（失败），之后反复抓取平底锅失败。这同样源于 E5.5 的接口缺失。（2026-10-21 更正：此前误记为"平底锅半露在抽屉外"。）
- 下一步可选：
  1. 核实这一步开思考（每局只发生一两次，可以接受较长延迟）；
  2. 先补上区域列表（E5.5）再测核实；状态描述加入物体所在区域的符号关系（会改变观测设计，需权衡难度）；
  3. 平底锅等大件物体的搬运与放置（搬运途中停滞、放到柜顶失败）；
  4. 够不着的物体给出明确的失败原因，并让规划器知道无法补救。

### E5.4 计分器 v6：探索前缀不计顺序（R11）

r3 中 case8 的各方法都正好停在 8/15。逐局核对发现，智能体其实把任务完整做完了：翻抽屉找到碗、倒入布丁和饼干、把碗放到柜顶。问题出在计分：

- 官方子目标是每个物体一条严格有序的链。碗的链是"开上层→关上层→开中层→关中层→开下层→抓碗→放桌上→抓碗→放柜顶"，前 5 步就是演示者翻找抽屉的路径。
- 智能体换了一种同样合理的翻找顺序：三个抽屉都打开，取碗被上层挡住后，再把中层和上层关上。
- 计分链因此卡在第 2 步"关上层"之后，等待"开中层"，而中层早已打开又关上了。其后已完成的 7 个子目标全部不计。

60 个任务中有 42 条物体链以开关步骤开头（Memory_Execution 14 条、Memory_Exploration 10 条、Mix 12 条等）；只有微波炉一类任务把开门放在链中间，那里开门是真实的前置条件。

修正（`exp/scoring.py`，v6）：
- 链开头连续的开/关步骤各自独立计分：open X 在 X 曾被打开时计入；close X 在 X 打开过之后又关上时计入。
- 其后的操作步骤照常按顺序推进，且不必等探索前缀全部完成。
- 链中间的开/关保持顺序。
- 官方原始计分不变，照常并列报告。

验证：演示回放与 v5 完全相同（整任务 37/40，子目标 400/405，没有任何任务变化），v5 的结果另存为 `exp/runs/e05/oracle_replay_v5.csv`。重算：r3 共 110 局，其中 39 局变化（case5 全部 20 局每局 +6 个子目标；case8 有 19 局从 8/15 变为 15/15 整任务成功）；r2b 共 145 局，其中 27 局变化（见 E5.3 第 6 条）。

### E5.5 评分目标对规划器不可达（2026-10-21 发现，r4 修正）

整理 case5 时发现，子目标"平底锅放到灶台区域 `flat_stove_1_cook_region`"引用的是灶台模型自带的站点。这个站点没有在任务场景定义（BDDL）中声明，因此不在 `env.regions` 里，而提供给模型的区域列表、Jev 候选动作和动作校验都来自 `env.regions`。结果是任何规划器都无法发出"放到灶台"的动作；慢分支即使建议"放到灶上"，快分支也选不到。

扫描全部 60 个任务（`exp/x_scan_goal_targets.py`）：
- 10 个任务各有 1 个子目标引用了未声明的站点：7 个是灶台 `cook_region`（Ideal case7、Memory_Exploration case3/4/5、Mix case2、Observation_Mismatching case7、Random_Disturbance case7），3 个是木托盘 `contain_region`（各类型的 case10）。
- 这些任务对 LLM 方法而言，整任务成功的上限为 0。
- 已跑过 LLM 实验的任务中，只有 Memory_Exploration case5 受影响：r2b、r3 中 case5 各方法 0/5 的直接原因就在这里。方法间的完成率比较仍然有效，因为各方法的上限相同，都是 13/14。

修正（工作副本，r4 起生效；r3、r3b 冻结代码不变）：`rc_env.agent_regions(env)` 在 `env.regions` 之外补上物体自带的功能性站点，排除 `*_init_region`。全部任务中只会补进三类站点：`cook_region`（7 个任务）、`contain_region`（3 个）、`center_region`（3 个）。`run_dual_shared_episode.py` 的区域列表改用该函数。标准计划运行器直接使用站点名，不受影响。
