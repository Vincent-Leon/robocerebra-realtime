# vLLM 前缀缓存调研（组会行动项 2，2026-10-21）

对象：L20 实验实例，vLLM v0.27.1，Qwen3.8-27B（Qwen3_5 架构：48 层 Gated DeltaNet 线性注意力 + 16 层全注意力），FP8 权重，单卡，开启前缀缓存。
依据：vLLM v0.27.1 源码与相关 PR（调研代理逐文件阅读，PR 首次进入的正式版用 `git tag --contains` 确认）。

## 已核对的事实

- **命中粒度 784 token 是自动算出的块大小，不是故障。** 实验容器的启动日志写明：
  - `Setting attention block size to 784 tokens to ensure that attention page size is >= mamba page size.`
  - `Mamba cache mode is set to 'align' for Qwen3_5ForConditionalGeneration by default when prefix caching is enabled`
- **784 的算法**（源码 `vllm/platforms/interface.py::_align_hybrid_block_size`）：注意力块的一页（单层）不能小于一层 GDN 状态，再按 16 对齐。
  - 注意力 KV：4 个 KV 头 × 256 维 × (K+V) × 2 B = 每 token 4 KiB。
  - 一层 GDN 状态 3,207,168 B，其中：
    - fp32 递归态：48 × 128 × 128 × 4 B = 3,145,728 B；
    - bf16 卷积态：61,440 B。
  - ⌈3,207,168 / 4,096⌉ = 783，向上取到 16 的倍数，得 784。
- **`cache_salt`**：OpenAI 兼容接口支持按请求传入（`vllm/entrypoints/openai/chat_completion/protocol.py`），只进入首块的哈希（`vllm/v1/core/kv_cache_utils.py`）。因此每个请求用不同的随机 salt，就能在**输入 token 完全相同**的条件下让命中归零。

## 实测（2026-10-21，L20 实验实例，同一段约 3,551 token 的提示依次请求）

| 请求 | 命中 token | 延迟 |
|---|---|---|
| 首次（冷启动） | 0 | 1.61 s |
| 重复，不加 salt | 3,136（= 4 × 784 = ⌊3,550/784⌋ × 784） | 0.26 s |
| 重复，随机 `cache_salt` | 0 | 1.52 s |
| 再重复，不加 salt | 3,136 | 0.26 s |

结论：
- 命中粒度与上限都符合源码机制（整块，最多到提示长度 − 1）。
- 用 `cache_salt` 禁缓存有效，而且不会挤掉原有缓存。
- 约 3.5k token 的提示，命中后预填充从 1.6 s 降到 0.26 s。

工作副本已实现 `run_dual_shared_episode.py --bust_mode=salt`（默认；`nonce` 为 r2/r3 的旧做法）。

## 机制要点（据源码，未逐条实测）

1. 块哈希由父块哈希、本块 token、额外键（LoRA、图像标识及其块内偏移、cache_salt）计算，逐块成链；只缓存满块；按 LRU 淘汰；命中最多到 prompt 长度 − 1。`cached_tokens` 需要启动参数 `--enable-prompt-tokens-details`（我们已开启）。
2. 混合模型在 `align` 模式下，GDN 状态只能在一次前向结束时保存。调度器把 prefill 切在块边界上，检查点有三个来源：
   - prompt 最后一个整块的边界；
   - 每个 prefill chunk 的末端（L20 默认每步 2048 token，约每 1568 token 一个）；
   - 共享前缀的交汇点（v0.24 起）。
   命中位置 = 全注意力连续命中范围内、最右边一个有 GDN 检查点的块边界。
3. 没有"钉住某段前缀不被淘汰"的接口（相关 issue #23083、#23641 以 not planned 关闭）；调度只有 fcfs / priority，priority 不影响淘汰。前缀相同的请求自动共享物理块，快慢两个分支不需要任何额外机制。
4. 调小粒度的选项与代价：
   - `--block-size` 只能调大；
   - FP8 KV 反而会变成 1568；
   - `--mamba-ssm-cache-dtype bfloat16` 可降到 400，但偏离了模型指定的 fp32 递归态，精度要自测；
   - `--prefix-match-unit`（v0.26+）只在 prompt 末尾建细检查点，对只追加历史的布局没有收益。
5. vLLM 内置的 LMCache 连接器在 v0.27.1 不支持混合模型；原生 OffloadingConnector（`--kv-offloading-size`）可以把缓存扩到 CPU 内存。

## 对本项目的含义（按机制推断）

- 相邻两次调用的共享前缀 D = 系统提示 + 静态块 + 上一次的历史，命中约为 ⌊D/784⌋×784。也就是说，平均每次要重算约半块（≈392 token）的共享前缀，再加上整段易变尾部（图像、当前状态、模式指令）。这与实测命中率 45–66% 相符：易变尾部和不满一块的余数加起来占了提示的三到五成。
- 当前布局是对的：图像、当前状态、慢分支建议都放在历史之后，不改变前面各块的哈希。建议注入不会破坏缓存。
- 可改进的地方：
  1. 禁缓存对照改用随机 `cache_salt`：输入 token 与实验组完全一致，比现在"在系统提示开头加随机串"更干净。r2、r3 的禁缓存组用的是随机串，结论不受影响，新一轮起切换。
  2. 若要测"更细粒度能否进一步降延迟"，可另起一个 `--mamba-ssm-cache-dtype bfloat16` 实例（块大小 400），比较命中率、决策延迟与决策一致性。代价是递归态精度下降，需先确认动作选择不受影响。
  3. 前缀里不放时间戳、步数等易变字段（当前已满足）。历史需要截断时一次截一大段，截断后让稳定前缀对齐到 784 的整数倍。
- 版本提醒：从 v0.27.1 到当前最新正式版 v0.32.0，混合缓存的改动很多：
  - v0.29 起检查点保留策略改为参数，默认只保留 prompt 末尾与交汇点的检查点；
  - v0.32 删除了 `all` 模式。
  升级服务前要先重测命中率。
