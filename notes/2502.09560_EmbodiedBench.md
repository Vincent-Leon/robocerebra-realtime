# EmbodiedBench: Comprehensive Benchmarking Multi-modal Large Language Models for Vision-Driven Embodied Agents

> 阅读日期：2026-10-16。来源：`papers/2502.09560_EmbodiedBench_MLLM_embodied_agents.pdf`（arXiv v3，56 页，全文含附录 A–K 已读完）；代码：`repos/EmbodiedBench`（HEAD `9be4e98` "Fix EB-ALFRED split instructions"，2026-05-30；只浏览未运行）。页码均指 PDF 页码。

## 基本信息

- **作者 / 机构**：Rui Yang*, Hanyang Chen*, Junyu Zhang*, Mark Zhao*, Cheng Qian, Kangrui Wang, Qineng Wang, Teja Venkat Koripella, Marziyeh Movahedi, Manling Li, Heng Ji, Huan Zhang, Tong Zhang；UIUC、Northwestern、Toronto、TTIC（p.1）。
- **发表**：ICML 2025（PMLR 267）；arXiv 2502.09560v3（2025-06-05）（p.1）。README 的 BibTeX 指向 OpenReview `DgGF2LEBPS`。
- **资源**：项目页 https://embodiedbench.github.io ；代码 https://github.com/EmbodiedBench/EmbodiedBench ；数据集 HF `EmbodiedBench/EB-ALFRED`、`EmbodiedBench/EB-Manipulation`（README）。2025-06 另发布多模型轨迹数据集；2025-10 发布后续工作 ERA（训练配方）；README 称将用于 CVPR 2026 FMEA Workshop 挑战赛。
- **规模**：4 个环境、1,128 个测试实例（300+300+300+228）、6 个能力子集、24 个 MLLM（8 专有 + 16 开源）（p.1, p.3 Table 1, p.5-6）。
- **贡献自述**：(1) 覆盖不同动作层级与细粒度能力子集的 benchmark suite；(2) 一个高效的 MLLM agent 框架；(3) 大规模评测与消融（p.2）。

## 一句话总结

EmbodiedBench 是一个**回合制、静态环境**下评测 MLLM 具身 agent 的套件：用统一的 Gym 风格封装把 AI2-THOR（EB-ALFRED、EB-Navigation）、Habitat 2.0（EB-Habitat）、CoppeliaSim（EB-Manipulation）接到同一个"视觉描述→反思→推理→语言计划→可执行计划"的 JSON agent 框架上，评测 24 个模型后发现：MLLM 在高层规划任务上尚可（最佳约 64–68%），在低层操作上很弱（最佳 GPT-4o 平均 28.9%），长程规划是最难子集，视觉输入对低层任务至关重要而对高层任务几乎无用；整个协议中模型推理期间世界完全静止，论文与代码均不涉及延迟、实时或异步概念。

## 问题设定与动机

- **动机**：已有 agent 评测要么纯文本（ALFWorld、AgentBench、Lota-bench、Embodied Agent Interface），要么只覆盖高层任务（VisualAgentBench），缺少对"视觉在具身任务中的作用"和"MLLM 在导航/操作等低层任务上的表现"的系统评测（p.1-3，Table 1 p.3）。
- **动作层级定义**（p.3）：low-level action = 机器人可直接执行的原子命令，例如 7 维末端位姿 `a = [X, Y, Z, Roll, Pitch, Yaw, Gripper]` 或 "move forward 0.1 m"；high-level action = 可分解为低层原语序列 `a^h = [a_1, ..., a_n]`，例如 "find a HandTowel"。
- **形式化**（p.3）：语言条件 POMDP `(S, A, Ω, T, O, L, R)`；回报 `r_t = 1 iff s_t ⊨ L`；agent 维护历史 `h_t = (I_0, a_0, ..., I_{t-1}, a_{t-1}, I_t)`，策略 `π(a_t | L, h_t)`；目标 `max_π E[r_τ]`，τ 为任务完成或达到最大 horizon 的终止步。**注意**：这里的 t 是离散回合步，不是 wall-clock；观测只在动作之间采样。
- **两个设计特性**（p.2）：(1) 任务覆盖高层（EB-ALFRED、EB-Habitat）与低层（EB-Navigation、EB-Manipulation）；(2) 能力导向的细粒度评测（六个子集）。

## 核心设计

### 四个环境

| 环境 | 底层仿真器（代码版本） | 任务来源与改造 | 动作接口 | 观测与反馈 | 规模 / 最大步数 |
| --- | --- | --- | --- | --- | --- |
| **EB-ALFRED** | AI2-THOR（`ai2thor==2.1.0`，经 Lota-Bench 的 `ThorEnv`/`ThorConnector` 实现；`conda_envs/environment.yaml`） | ALFRED valid-seen 集；8 类高层技能 pick up / open / close / turn on / turn off / slice / put down / find，各带对象参数；相对 Lota-Bench 增加多实例支持（对象后缀 `Cabinet_2`，补全 7 种任务类型含 Pick Two & Place）、把所有 put down 合并为单一动作、修复仿真 bug 与指令质量（p.3-4, p.19） | 离散动作 id → 自然语言技能；动作空间随场景动态变化，171–298 个（p.4, p.19） | 第一人称 RGB + 文本反馈（有效/无效及失败原因，如 "already holding"）（p.3, p.19） | 300（6 子集 × 50）/ 30 步（p.5-6） |
| **EB-Habitat** | Habitat 2.0（`habitat-sim==0.3.0 withbullet headless` + habitat-lab v0.3.0；README） | Language Rearrangement benchmark（282 指令模板，YCB + ReplicaCAD）；70 个高层技能，5 类 navigation / pick / place / open / close；导航只能到 receptacle，需多次移动寻物；PDDL 评估任务与子目标（p.4, p.19） | 离散 0–69（p.35 prompt） | 第一人称 RGB + 文本反馈（p.19） | 300（6 × 50，由原数据集子集重组而成）/ 30 步 |
| **EB-Navigation** | AI2-THOR（`ai2thor==5.0.0`，`platform=CloudRendering`；`EBNavEnv.py`） | 自建：AI2-THOR 90 个场景各 1 个导航任务，含初始位姿、目标对象信息、语言指令；提供自动任务生成脚本（可调初始距离 α、随机种子）（p.4, p.20） | 8 个离散低层动作：前/后/左/右移 0.25 m、左/右转 90°、相机上/下 30°（p.36；代码 `DISCRETE_SKILLSET`） | 第一人称 RGB + 仅"有效/无效"（碰撞）反馈；成功 = 与目标的水平距离 ≤ 阈值（代码 `SUCCESS_THRESHOLD = 1`）（p.20） | 300（5 × 60，无 Spatial 子集）/ 20 步 |
| **EB-Manipulation** | CoppeliaSim V4.1.0 + PyRep（VLMBench/AMSolver 扩展）；7-DoF Franka Panda（p.20） | 4 类任务 Pick & Place / Stack / Shape Sorter / Table Wiping，颜色、位置、形状、朝向随机（p.20） | 7 维离散向量 `[x, y, z, roll, pitch, yaw, gripper]`：位置 100 bins、姿态 120 bins（每 bin 3°）、gripper 0/1；`ABS_EE_POSE_PLAN_WORLD_FRAME` 模式——环境内部自动运动规划并执行到目标位姿（p.4-5, p.20-21） | 前视 RGB + YOLO 检测框（按 Y 坐标排序编号）+ 各可见物体的离散 3D 坐标 + 坐标系标注（p.5, p.21） | 228（4 子集 × 48 + Visual 36，Table Wiping 不进入 Visual 子集）/ 15 步 |

代码层面对"技能到底是什么"的核对（与第 6 节"实时推进"直接相关）：

- EB-ALFRED 的 `find` 由 `envs/eb_alfred/thor_connector.py::nav_obj()` 实现：计算目标最近可达点，对最多 20 个候选位置 × 5 个 horizon 偏移反复发 `TeleportFull`，直到目标可见——**是瞬移，不是逐步导航**；pick/put/open 等也是单个 AI2-THOR 动作。加热/冷却/清洗等对象状态由 Python 侧 `ThorEnv.update_states()` 维护，不是仿真内生过程。
- EB-Habitat 的技能是 `envs/eb_habitat/actions.py::PddlHlAction`：从 PDDL 域取出动作并 `apply_if_true(sim_info)` 直接写入状态；`nav` 的后置条件就是 `robot_at_closest(entity)`（`config/task/pddl_domain_replica_cad.yaml`）——**谓词级瞬时跳变，没有物理执行过程**。
- EB-Navigation 每个动作是一次 `controller.step(action="MoveAhead", moveMagnitude=0.25)` 等离散瞬时位移。
- EB-Manipulation 是唯一有真实物理执行时间的环境：`amsolver/task_environment.py::step()` 内 `while not done: done = path.step(); self._pyrep.step(); self._task.step()` 把整段规划轨迹**在一次 `step()` 调用里阻塞跑完**，Python 侧拿不到中间观测、不能打断。

### 六个能力子集（定义 p.5；示例 Table 5 p.23）

| 子集 | 考察点 | 构建方式 |
| --- | --- | --- |
| Base | 基础任务求解（低到中等难度） | ALFRED：oracle 步数 <15 的 50 条；Habitat：合并 new scenes / novel objects / instruction rephrasing；Nav：从 90 个任务采样 60；Manip：从 VLMBench 选取（p.19-21） |
| Common Sense | 间接指称（"能保鲜几天的容器"） | ALFRED/Manip：GPT-4o 对 base 指令增强；Nav：GPT-4 增强（p.20）；Habitat：context 子集 |

### Agent 框架与 prompt 结构（Fig. 2 p.4；§4.3 p.5-6；Appendix I p.33-49）

- **输入**：语言指令；视觉观测（默认只用当前帧，论文明确说多帧会让模型困惑，p.5）；文本 ICL 示例（ALFRED 10 条、长程子集 7 条；Habitat 10 条；Nav 3 条；Manip 按任务 2/4/4/8 条，p.41）；交互历史（每步 `action id, 动作名, env feedback`）；任务特定信息（高层任务与 Nav 给技能/动作列表；Manip 给动作空间描述、检测框与物体坐标）。
- **输出**：JSON（schema 见 p.48-49；代码 `planner/planner_config/generation_guide*.py`），五段：`visual_state_description` → `reasoning_and_reflection` → `language_plan` → `executable_plan`（`{action_id, action_name}` 列表；Manip 为 7 维离散向量列表）。
- **多步规划**：一次输出整段动作序列，环境逐个执行；遇到无效动作或任务完成即中断并从最新状态重新规划（p.5-6；`evaluator/eb_alfred_evaluator.py` 的 for 循环）。好处是贴合 ICL 示例、减少 API 调用：EB-Manipulation 中 GPT-4o 平均 2.6 次规划 vs 12.9 个环境步（Table 8 p.25）。
- **停止条件**（p.18）：达到最大步数；任务成功；累计无效动作 >10（代码 `_max_invalid_actions = 10`）；输出空计划。
- **Prompt 模板**（p.34-38；`evaluator/config/system_prompts.py`）：角色设定 → 各技能的"有效性规则"（如 Find "always valid"）→ 动作 id 列表 → ICL → Guidelines（计划 ≤20 动作、先 find 再交互、不要重复、多实例、根据反馈反思）→ 指令 → 历史与反馈 → 输出格式要求。EB-Navigation 另有"策略"段（少用旋转、尽量贴近目标等）。
- **解码设置**：温度 0，最大完成 token 2048（p.6；代码 `remote_model.py` 为 4096），图像统一 500×500（p.6）。
- **EB-Navigation 特例**：默认开启带图多轮 `chat_history`（Appendix G p.30-31：专有模型受益，开源模型不一；代码提供窗口与 `truncate`）。
- **可选模块**（README 配置项）：`language_only`、`detection_box`、`multistep`、`multiview`、`visual_icl`、`resolution`、`n_shots`、`env_feedback`；四者互斥。

### 模型接入方式（Appendix D p.21；README；`planner/remote_model.py`）

- 论文：专有模型走 API，开源模型用 `lmdeploy` 与 `vllm` 本地部署（p.21）。
- 代码 `RemoteModel`（382 行）按 `model_name` 分派：`claude*` → `anthropic` SDK；`gpt*` → `openai` SDK 并用 `response_format=json_schema`；`gemini*` → Google 的 OpenAI 兼容端点 + `beta.chat.completions.parse`（pydantic `ActionPlan`）；`qwen*` → DashScope OpenAI 兼容端点；`Qwen2/2.5/3-VL`、`InternVL`、`Llama-3.2-Vision` → `OpenAI(base_url=remote_url)` 指向自建 OpenAI 兼容服务（README 用 `lmdeploy serve api_server`）；`model_type=local` → 进程内 `lmdeploy.pipeline(PytorchEngineConfig(session_len=12000, dtype='float16', tp))`；`model_type=custom` → `planner/custom_model.py` 以 multipart（图片文件 + 文本）POST 到 `server.py` 的 Flask `/process`（Phi-4-multimodal、Ovis2、gemma-3 的 HF transformers 实现）。
- 消息统一为 OpenAI chat 格式（图像 base64 data URL），`planner_utils.convert_format_2claude / 2gemini` 做转换；`fix_json` 修复常见 JSON 错误；不支持 json schema 的模型在 prompt 末尾追加格式模板。

### 评测指标

- 主指标：**task success rate**（p.6）；Table 2/3 的子集成功率是整数（每子集 50 条）。
- 补充：subgoal success rate（高层任务，PDDL 子目标比例，Table 6 p.24）；平均 planner 步数与环境步数（Table 7-8 p.25，论文强调二者不是精确性能指标）；每轨迹格式错误数（Table 12 p.33）；错误类型分布（Fig. 6 p.9，Fig. 17 p.31，Table 11 p.32）。
- 代码每 episode 记录：`task_success`、`task_progress`、`reward` 均值、`num_steps`、`planner_steps`、`planner_output_error`、`num_invalid_actions(_ratio)`、`episode_elapsed_seconds`（episode 开始至今的 wall-clock，仅此一项与时间有关）；`evaluator/summarize_result.py` 对所有数值字段取平均。

## 实验与主要结果

- **模型**（p.6；Table 4 p.22）：专有 8 个——GPT-4o、GPT-4o-mini、Claude-3.7-Sonnet、Claude-3.5-Sonnet、Gemini-1.5-Pro、Gemini-2.0-flash、Gemini-1.5-flash、Qwen-VL-Max；开源 16 个——Llama-3.2-Vision 90B/11B、InternVL2.5 78B/38B/8B、InternVL3 78B/38B/8B、Qwen2-VL 72B/7B、Qwen2.5-VL 72B/7B、Ovis2 34B/16B、gemma-3 27B/12B。
- **高层 vs 低层（核心发现）**（p.6，Table 2 p.7，Table 3 p.8）：
  - 高层：Claude-3.5-Sonnet EB-ALFRED 64.0 / EB-Habitat 68.0；Claude-3.7-Sonnet EB-ALFRED 67.7（Table 2 中最高，但正文仍说 Claude-3.5 最高）；GPT-4o 56.3 / 59.0。
  - 低层：GPT-4o 最佳，EB-Navigation 57.7、EB-Manipulation **28.9**；Claude-3.7 45.0 / 28.5；Claude-3.5 44.7 / 25.4；Gemini-2.0-flash 48.7 / 16.7；GPT-4o-mini 32.8 / 4.8。
  - 开源最佳 InternVL3-78B：EB-Habitat 55.0、EB-Navigation 53.7、EB-Manipulation 26.3，接近 GPT-4o；Ovis2-34B Manip 26.8。多个开源模型在 Manip 接近 0（Qwen2-VL-7B 0.0、Llama-3.2-11B 0.9）。开源模型随规模单调提升（p.6）。
  - 摘要原话：最佳模型 GPT-4o 在低层操作上"仅 28.9%"（p.1）。
- **视觉的作用**（p.6-7）：去掉视觉（Lang 版）GPT-4o EB-Navigation 57.7 → 17.4，长程子集 55.0 → 0；EB-Manipulation 28.9 → 16.2。高层任务反而持平或更好：GPT-4o (Lang) EB-ALFRED 58.0 vs 56.3，EB-Habitat 56.0 vs 59.0。引言概括为低层任务去视觉掉 40%–70%（p.2）。
- **子集差异**（p.6）：长程最难——EB-Habitat Claude-3.5 base 96 → long 58，GPT-4o 86 → 64；模型间排序随子集变化（GPT-4o 在 Habitat 长程 64 > Claude-3.5 58）。
- **语言侧消融**（EB-ALFRED base，Fig. 4 p.7）：去环境反馈 GPT-4o 64 → 54、Claude-3.5 72 → 64；ICL 0/5/10-shot：GPT-4o 40/46/64，Claude 46/52/72。
- **视觉侧消融**（EB-Manipulation base，Fig. 5 p.7；Appendix F p.25-30）：分辨率 300/500/700：GPT-4o 22.9/39.6/35.4，500 最优；去检测框 GPT-4o 39.6 → 27.1、Claude 37.5 → 29.2；多步历史图像有害 GPT-4o 31.3 vs 39.6；多视角有害 GPT-4o 31.3 vs 39.6（Nav 50.0 vs 61.7）；视觉 ICL 显著有益 Claude 41.7 vs 25.0（+16.7）、GPT-4o 35.4 vs 27.1。EB-Navigation 中多个检测框反而有害（GPT-4o 53.3 vs 61.7），单框最好 68.3（Table 9 p.26），故 Nav 默认不画框。
- **chat history**（Table 10 p.31）：EB-Navigation GPT-4o 57.7 vs 无历史 45.3，长程 55.0 vs 15.0；Qwen2-VL-72B 反而 21.2 vs 36.3。
- **错误分析**（GPT-4o，每子集抽 10 条失败共 110 条，p.9；Nav 见 p.31-32）：EB-ALFRED 规划错误 55%（缺步骤 23%、无效动作 22%）、推理错误 41%（反思错误 17%、过早终止 13%）、感知 4%；EB-Manipulation 规划 44%、感知 33%（错误识别 22%）；EB-Navigation 推理 46%、感知 31%、规划 23%。
- **效率**（Table 7-8 p.25）：多步规划把模型调用次数降低约 50%–80%；GPT-4o EB-ALFRED 4.4 次规划 / 16.3 步，EB-Manipulation 2.6 / 12.9。
- **格式错误**（Table 12 p.33）：小模型多（InternVL2.5-8B 每轨迹 8.04 次），GPT-4o 0.0067。
- **子目标成功率**（Table 6 p.24）：普遍高于任务成功率；Gemini-1.5-Pro EB-ALFRED 子目标 67.4 高于 Claude-3.5 65.3，但任务成功率更低。

## 与本项目的关系

### 对照计划文档的定位

- 计划 §2 把 EmbodiedBench 描述为"统一观测与环境接口，支持本地和 API 模型，覆盖导航与操作"，§5.1 列为 P2（复用多模态输入、模型 API 接口、导航与操作任务；新增每个底层环境的实时与事件适配），§9 阶段 5 作为跨基准验证的备选，并提醒"统一 Gym API 不意味着只加外层 wrapper 就能让底层仿真实时运行"。
- 本次精读**证实并加强**了这一提醒：EmbodiedBench 不只是"没有实时时钟"，它的高层技能本身就是瞬时的符号跳变（ALFRED `TeleportFull`、Habitat PDDL 谓词），低层环境里 Nav 是瞬时位移、Manip 是阻塞式内部运动规划。要满足计划 §4.1 的"技能消耗真实仿真时间、可失败、有明确中断语义"，需要**重写技能层**而不只是加时钟。
- 计划 §7.1 的"暂停环境参考"条件：EmbodiedBench 原协议表面上等价于"推理期间冻结环境"，但由于技能瞬时完成，它连"动作执行时推进"这一半也不满足；因此原始 EmbodiedBench 分数应如计划所说"另列为 Original"，不能当作本项目的暂停环境参考。

### 可直接复用（做 API 模型评测）

- `planner/remote_model.py`：多厂商统一接入（Anthropic / OpenAI / Gemini 兼容端点 / DashScope / 任意 OpenAI 兼容本地服务）与 json schema 约束输出；`planner_utils.py` 的格式转换、pydantic schema、`fix_json`、历史截断。可作为我们"闭源 API + 开源模型 + 不同 harness"接入层的起点。
- `planner/vlm_planner.py`：prompt 组装（系统规则 + 技能列表 + ICL + 历史反馈）、多动作计划解析（`json_to_action` 返回 -1 无效 / -2 空计划）；五段式 JSON 可作为慢分支输出格式参考，`executable_plan` 列表天然就是"计划版本"的载体。
- Evaluator 的 episode 日志结构（每步 `reasoning`、`env_feedback`、`action_id`、`last_action_success`）与 `summarize_result.py`，可扩展加入时间戳字段。
- 技能"有效性规则"写法（prompt 中逐条列前置条件）与我们 §4.1 的技能接口说明风格一致。
- **复用成本**：`remote_model.py` 顶层硬 `import lmdeploy`、`google.generativeai`、`anthropic`；`vlm_planner.py` 顶层 `import torch, cv2`——仅做 API 评测也需装这些依赖，或先剥离为可选导入。
- **必须改掉的时序行为**：`vlm_planner.act()` 对 Gemini 每次调用后 `time.sleep(15)`，异常后 `sleep(60)`（本地 20 s）重试一次；evaluator 捕获异常后 `sleep(30)` 继续；模型调用是同步阻塞 `respond()`；没有请求发送/返回/动作生效时间戳，只有 `episode_elapsed_seconds`。这些与计划 §7.1-7.2 的延迟记账相冲突，需要替换为异步调用 + 完整时间戳。

### 每个底层仿真器"实时推进"的难点

| 环境 | 现状 | 实时化难点与可能路径 |
| --- | --- | --- |
| EB-ALFRED（AI2-THOR 2.1.0） | 世界只在 `Controller.step()` 时推进并返回 event；两次 step 之间 Python 侧拿不到观测；`find` 是 TeleportFull，pick/put 是单动作，没有"执行中"状态可打断；对象状态（加热等）由 Python 维护 | (a) AI2-THOR 的 Controller 是单 socket 请求-响应，不能并发调用，需要一个仿真时钟线程以固定频率发推进命令（AI2-THOR 提供 `AdvancePhysicsStep`/`PausePhysicsAutoSim` 一类动作，具体可用性需按版本实测）并把 agent 动作与时钟 tick 串行化到同一队列；(b) 把 find/pick/put 重写为多步低层动作（AI2-THOR 有 `MoveAhead`/`GetShortestPath` 等）才能有耗时与中断语义；(c) 代码基于 2019 年的 ai2thor 2.1.0 旧 API（`Controller.start(x_display=...)`），升级到 5.x 等于重写 `ThorConnector`。**结论：AI2-THOR 不能在 EmbodiedBench 的封装下独立于 agent 推进时间；需要自建时钟并重写技能层。** |
| EB-Habitat（habitat-sim 0.3.0） | 技能是 PDDL `apply_if_true` 直接写状态；habitat-sim 本身可按 dt 步进物理，但 Language Rearrangement 任务层绕过了物理执行 | 需用 habitat-lab 的 oracle 导航/机械臂控制器或学习技能替换 PDDL 技能，再加时钟与事件；工作量最大，且 Habitat 技能/传感器配置（Hydra 结构化配置）复杂。 |
| EB-Navigation（AI2-THOR 5.0.0） | 8 个瞬时离散动作，无连续运动；每步立即返回 | 依赖最少、代码最短（473 行），最适合作为 AI2-THOR 实时化试点：把离散位移替换为连续速度/多帧插值，用时钟线程推进并注入动态障碍；但无效动作索引会被 `np.random.randint(8)` 随机替换，需移除。 |
| EB-Manipulation（CoppeliaSim + PyRep） | 唯一有真实物理执行时间的环境，但 `_path_action` 的 while 循环在一次 `step()` 内阻塞跑完；规划失败抛异常被 wrapper 吞掉（reward -1） | 需把路径执行拆成"每次 `pyrep.step()` 后检查中断/事件"的可调度循环；PyRep 是单线程同步 API，仿真时钟必须占主线程，推理放独立进程；要补充取消语义（取消耗时、手持物体处理）。与我们 P0（LIBERO/OpenVLA 执行栈）相比，这里底层是运动规划器而非 VLA，控制器会替模型完成轨迹。 |

共同点：四个 wrapper 的 `step()` 都是"收到动作→同步阻塞到效果落定→返回 obs"，没有 `tick()`/`advance(dt)`；evaluator 是单线程 while 循环，`planner.act()` 期间不触碰环境。计划 §7.1 的三类运行条件都要在 wrapper **之下**增加时钟与事件层，而不是在 evaluator 之上包一层。

### 引用时的措辞注意

- 写作"回合制/静态环境下评测 MLLM 高层规划与低层控制能力的 benchmark"，不要写成"支持实时或异步评测"；论文全文无 latency / real-time / asynchronous 讨论。
- 它的"low-level"是"离散化末端位姿关键点 + 环境内自动运动规划"（Manip）或"0.25 m 离散位移"（Nav），不是关节级或速度级控制；引用时要注明运动规划器承担了轨迹生成。
- "统一 Gym 接口"在实现上是 4 套独立 conda 环境、两种 gym（`gym` 0.23/0.26 与 `gymnasium` 1.0）、`step()` 签名不一致（Nav 多一个 `i_flag`，Manip 返回 `last_frame_obs` dict 与 `(description, obs)`）；不要据此声称"一套接口可直接复用"。
- 数字引用用 v3 版本并注明：Table 2 中 Claude-3.7-Sonnet EB-ALFRED 67.7 高于正文所说的 Claude-3.5 64.0；"去视觉掉 40–70%"只是 GPT-4o/GPT-4o-mini 的 Lang 对照。
- README 指出 EB-ALFRED 环境（`find` 偶尔瞬移出房间或误报成功）与数据集（SprayBottle 指令）在论文后有修复，复现论文数字需 commit `5fdee379`；EB-Habitat 长程数据集也更新过（Issue #28/#39）。
- 代码后续加入的 Qwen3-VL、gpt-5 分支、ERA 等不属于 ICML 版本，引用时区分。

### 环境封装方式

- 每个环境是 `gym.Env`（Manip 为 `gymnasium.Env`）子类：`reset()` 返回 obs（dict `{'head_rgb': ndarray}`；Manip 返回 `(description, obs)`），`step(action)` 返回 `(obs, reward, done, info)`；`info` 含 `task_success`、`task_progress`、`env_feedback`（自然语言）、`env_step`、`last_action_success`、`action_id`、`action_description`、`reasoning`、`episode_elapsed_seconds`；`language_skill_set` 为自然语言动作列表（ALFRED 每个 episode 动态重建）；`save_image()`、`save_episode_log()` 写到 `running/<env>/<exp_name>/`。
- 数据：Nav 与 Habitat 子集数据随仓库提供；EB-ALFRED 与 EB-Manipulation 数据需从 HF 下载（git lfs）；Habitat 还需 `habitat_sim.utils.datasets_download --uids rearrange_task_assets`。

### 模型接口文件

`planner/remote_model.py`（多厂商 + lmdeploy 本地）、`planner/custom_model.py` + `server.py`（HTTP 自定义模型）、`planner/planner_utils.py`（格式转换、schema、`fix_json`、`truncate_message_prompts`）、`planner/planner_config/generation_guide.py` 与 `generation_guide_manip.py`（输出 JSON schema）。

### 安装难度与硬件要求

- 需 3 个 conda 环境（ALFRED+Habitat、Nav、Manip）加可选 lmdeploy 环境；四个 yaml 都是 **linux-64 导出**（`_libgcc_mutex`、`ld_impl_linux-64`、`libgcc-ng`、`nvidia-*-cu12` wheel、`torch` 2.4/2.5），在非 Linux 上无法原样解析。
- 渲染：README 要求先运行 `startx.py` 启动 headless X server（脚本用 `lspci` 枚举 NVIDIA 设备并生成 Xorg 配置），默认 `DISPLAY=:1`；Docker 基于 `nvidia/cuda:*-ubuntu18.04`，`build.sh` 检查 `/proc/driver/nvidia/version`。
- EB-Manipulation：`CoppeliaSim_Pro_V4_1_0_Ubuntu20_04` 二进制 + PyRep + 复制 lua 插件，环境变量 `COPPELIASIM_ROOT`/`LD_LIBRARY_PATH`/`QT_QPA_PLATFORM_PLUGIN_PATH`。
- EB-Habitat：`habitat-sim==0.3.0 withbullet headless`（aihabitat conda 渠道）+ habitat-lab v0.3.0。
- 本地开源模型：README 给出 48 GB GPU 上 `tp = ceil(模型参数量 B / 10)` 的经验；API 评测本身不需要 GPU，但仿真器渲染需要 GPU（AI2-THOR Unity/Vulkan、habitat-sim EGL、CoppeliaSim OpenGL）。
- 安装难度：高——三套仿真栈、旧版本锁定（ai2thor 2.1.0、CoppeliaSim 4.1.0、habitat-sim 0.3.0）、X server 与 NVIDIA 绑定、git lfs 大数据。

### 能否在 macOS Apple Silicon 上运行（基于仓库文件推断，未实际安装）

- **按仓库流程，四个环境都不能直接运行**：conda yaml 全是 linux-64；`startx.py`/Docker 依赖 NVIDIA；CoppeliaSim 提供的是 Ubuntu tarball，PyRep 流程只给 Linux；habitat-sim `headless` conda 包是 Linux 构建；EB-Navigation 用 `CloudRendering`（Linux Vulkan）。
- **最接近可行的候选是 EB-Navigation**：只依赖 `ai2thor==5.0.0` + openai/anthropic 等纯 Python 包；AI2-THOR 历史上提供 macOS（x86_64 Unity）构建，理论上可改 `platform` 后借 Rosetta 运行，但 Apple Silicon 原生支持与 5.0.0 的 macOS 构建可用性**需验证**。EB-ALFRED 的 ai2thor 2.1.0 更旧，macOS 可行性更低。
- **现实方案**：Mac 上只跑 planner/模型接入层（纯 API 调用，剥离 lmdeploy/torch 导入后即可），仿真放 Linux GPU 机器，自建 RPC 把 `EBNavEnv` 等 wrapper 暴露出来；或直接用 Docker 镜像在远端运行完整栈。

## 局限与注意点

- **论文自述局限**：仅在仿真中评测，无真实机器人实验（p.9）。
- **协议层面**：静态、回合制，无任何时间维度；每步一张图；主指标只有成功率，无完成时间/成本/延迟指标（只有步数统计）；单次运行、温度 0、无方差与置信区间（每子集 50/60/48 条，Table 2 成功率为整数）。
- **技能过于理想化**：ALFRED `find` 是 oracle 瞬移且 prompt 声明"always valid"；Habitat 技能为 PDDL 谓词；两者都把导航与感知难度从评测中抹掉，所谓"高层任务不依赖视觉"的结论部分源于此（p.6-7 自己也指出高层任务更依赖文本信息）。
- **EB-Manipulation 的输入**：模型直接拿到各物体的离散 3D 坐标与编号检测框，本质是"读坐标做关键点规划"，并非从像素到控制；去掉检测框即大幅下降（p.8）。
- **论文内部不一致**：正文说 Claude-3.5-Sonnet 高层最佳（p.6），Table 2 中 Claude-3.7-Sonnet EB-ALFRED 67.7 更高；Appendix C.3 写 EB-Navigation "seven actions"（p.20），正文、prompt 与代码都是 8 个（p.4, p.36）；Appendix C 开头写"30 steps for high-level tasks (EB-ALFRED and EB-Navigation), 20 steps for EB-Navigation"（p.18），应为 EB-Habitat；最大完成 token 论文 2048（p.6）、代码 4096。
- **代码质量注意**：`EBHabEnv.step()` 里 `info['episode_elapsed_seconds'] = ... ,` 末尾多一个逗号（变成 tuple）；EB-Navigation 对越界动作随机替换；evaluator 对异常只 `sleep(30)` 后继续；`remote_model.py` 的 `if __name__ == '__main__'` 测试代码引用了不存在的 `template` 变量；四个环境 `step()` 签名不统一。
- **版本与复现**：README 提示 EB-ALFRED 环境修复（`find` 偶发瞬移出房间/误报成功）与数据集修复（SprayBottle 指令），复现论文需 commit `5fdee379`；EB-Habitat 长程数据集已就地更新（旧版 `long_horizon_old.pickle`）。
- **与本项目的差距**：没有事件、没有计划失效、没有中断语义、没有延迟注入；要用它做 P2 验证，第一步不是接模型，而是为某一个子环境（建议 EB-Navigation 或 EB-Manipulation）构建带时钟的技能执行层。
